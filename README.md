# 微服务 IM · spring-cloud-im

一套**可跑通的微服务即时通讯系统**：注册登录 → 加好友 → 实时聊天 → 历史消息 → 未读已读 → 撤回 → 后台管理。

>

>
> 建议开两个浏览器标签页分别登录不同账号，互相发消息看实时效果。

不是 Demo 拼图，而是一条**完整闭环**：消息先落库、再推送；推送丢了靠拉取补偿；token 会过期但不会莫名掉线。

> 技术栈：Spring Cloud Alibaba + Dubbo 3 + Netty + RabbitMQ + MySQL + Redis + Vue 3

## 一、功能特性

### 账号与安全

| 能力 | 说明 |
|---|---|
| 注册 / 登录 | BCrypt 存储；账号唯一性由唯一索引兜底（不靠"先查后插"） |
| 失败锁定 | 同一账号连续失败 5 次锁定 15 分钟（Redis 计数） |
| **滑动续期** | 剩余不足 5 分钟自动换新票；活跃用户不会被登出 |
| **强制下线** | 管理员踢人 = 断连接 + 作废 token，刷新也进不来 |
| 单端登录 | 同账号新登录踢掉旧连接（4001），客户端不重连 |
| 禁用 / 重置密码 | 后台操作，禁用后无法登录 |

### 社交

| 能力 | 说明 |
|---|---|
| 精确找人 | 按**完整账号**搜索，避免前缀模糊被批量抓取 |
| 好友申请 | 申请 → 同意/拒绝，MQ 实时推送（不是轮询） |
| 好友列表 | 含昵称与**在线状态**（读 `ws:online:{uid}`） |
| 注册自动加管理员 | 新用户开箱即有人可聊 |

### 消息

| 能力 | 说明 |
|---|---|
| 实时收发 | WS 上行 → Dubbo → 落库 → MQ 广播 → 对方 WS |
| ACK 回执 | 成功回 `seq`，失败回 `seq=0 + code + reason`；**永远有回执** |
| 历史分页 | `beforeSeq` 往前翻，首屏 30 条、每次 20 条 |
| 断线补缺 | 重连带 `afterSeq`，只补漏掉的那几条 |
| 未读 / 已读 | 未读 = `last_seq - last_read_seq`（减法，不存计数） |
| 撤回 | 2 分钟内可撤，软删（保留行保证 seq 连续） |
| 消息状态 | 发送中 / 成功(seq) / 失败(可点击重发) |

### 通知与体验

| 能力 | 说明 |
|---|---|
| 桌面通知 | 页面不可见时弹系统通知 |
| 标题未读 | `document.title = "(3) IM"` |
| 智能滚动 | 翻历史时新消息不抢滚动，只提示"↓ N 条新消息" |
| 时间分隔 | 跨天或间隔 >5 分钟才插时间 |

### 接入层防护

| 闸门 | 值 | 作用 |
|---|---|---|
| 协议单帧 | 64KB | 保护堆外内存 |
| 业务单帧 | 4KB | 避免把大字符串解码进堆 |
| **令牌桶** | 10 条/秒 · 桶 20 | 防单个连接刷屏（超限回 429） |
| 队列水位 | 4000 | 防所有人同时突发（超限回 503） |
| 出站水位 | 64KB/连接 | 慢客户端丢弃，不无限积压 |
| 空闲 | 60 秒 | 僵尸连接自动清理 |

## 三、一条消息的旅程

```
① 前端发 {"type":"MSG","cid":"c-1","to":2,"content":"在吗"}
② ws-gateway：4KB 检查 → 解析 → 令牌桶 → 丢业务线程池
③ Dubbo → im：
      好友校验(403) → 幂等查 cid → Redis INCR 取 seq
      → 写 1 行 im_message + 2 行 im_conversation_member（同一事务）
      → 事务提交后发 MQ
④ 回 ACK 给发送方：{"type":"ACK","cid":"c-1","seq":26}
⑤ 各 ws-gateway 实例消费 MQ → 查本机连接 → 推给对方
```

**两条独立的线**：ACK 只管"存住了没"，推送只管"对方在不在"。推送丢了不影响正确性——客户端重连会按 `afterSeq` 补齐。

## 五、关键设计取舍

| 主题 | 决定 | 理由 |
|---|---|---|
| **先落库再推送** | 落库成功才回 ACK | 推送是"加速器"，数据库才是真相 |
| **未读用减法** | `last_seq - last_read_seq` | 不存计数，永远不会算错 |
| **seq 连续** | 撤回也保留行（软删） | 删行会让补缺口和未读都错乱 |
| **两层大小闸** | 协议 64KB / 业务 4KB | 前者保堆外，后者避免解码大对象进堆 |
| **令牌桶限流** | 10/秒 · 桶 20 | 锁长期速率，放过人类连发突发 |
| **踢人=收卡** | 写 `auth:kicked:{uid}` | 断连接不够，要作废凭证，否则刷新即复活 |
| **签发权只在 auth** | 网关只验票 | 网关被攻破也不能伪造 token |
| **好友校验在后端** | im 内校验 | 前端隐藏输入框挡不住脚本直连 WS |

## 八、已知限制

- **单实例验证**：MQ 广播、在线表、踢人都是按多实例设计的，但目前只跑一台 ws-gateway
- **只有单聊**：群聊需要把会话模型从"两个 uid"扩成"成员表"
- **只有文本消息**：图片/文件/语音未实现（链路已设计：HTTP 上传 + fileId）
- **好友申请不支持删除好友/备注**（字段已留）
- **HS384 共享密钥**：网关持有签发密钥，上生产建议换 RS256 并改回 refreshToken 方案
- **无消息搜索、无多端设备管理**
