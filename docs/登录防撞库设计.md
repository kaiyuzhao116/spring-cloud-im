# 登录防撞库设计

> 关联代码：`auth/src/main/java/com/song/auth/service/AuthService.java`、`auth/.../manager/SessionManager.java`
> 关联配置：`jwt.max-fail-count`、`jwt.fail-window-seconds`
> 现状：已实现「账号维度失败计数 + 15 分钟锁定」，实测可返回 429

---

## 1. 要防的到底是什么

三个概念经常被混着叫，防护手段完全不同：

| 攻击 | 做法 | 特征 | 对应防护 |
|---|---|---|---|
| **暴力破解**（Brute Force） | 针对 1 个账号，穷举几百万个密码 | 单账号高频失败 | 慢哈希（BCrypt）+ 失败计数锁定 |
| **撞库**（Credential Stuffing） | 从别的站拿到「账号+密码」列表，批量试 | 大量**不同**账号，每个只试 1~3 次 | IP 限流 + 设备指纹 + 验证码 |
| **密码喷洒**（Password Spraying） | 用少数几个常见密码，试**大量**账号 | 每账号 1 次，永不触发账号锁定 | 全局失败率监控 + IP/ASN 维度限流 |

**当前实现防的是第一种和"单账号连续失败"的撞库**，防不住后两种——这是本文第 6 节要补齐的部分。

## 2. 当前实现（三行代码 + 两个 Redis 命令）

### 2.1 检查（每次登录第一件事）

```java
// 1. 失败次数过多直接拒绝，防撞库
if (sessionManager.getFailCount(account) >= jwtProperties.getMaxFailCount()) {
    throw new BizException(ResultCode.TOO_MANY_REQUESTS.getCode(), "失败次数过多，请 15 分钟后再试");
}
```

### 2.2 计数（密码错误 / 账号不存在时）

```java
long failCount = sessionManager.increaseFailCount(account, jwtProperties.getFailWindowSeconds());
```

### 2.3 清零（登录成功时）

```java
sessionManager.clearFailCount(account);
```

### 2.4 底层 Redis 命令

```redis
# 检查
GET    auth:fail:{account}          # 不存在 = 0

# 失败 +1 并续期
INCR   auth:fail:{account}
EXPIRE auth:fail:{account} 900

# 成功清零
DEL    auth:fail:{account}
```

### 2.5 配置

```yaml
jwt:
  max-fail-count: 5          # 达到 5 次即锁定
  fail-window-seconds: 900   # 计数窗口 = 15 分钟
```

## 3. 执行流程

```
POST /api/auth/login
        │
        ▼
  ┌─────────────────────┐
  │ GET auth:fail:{acc} │  0.3ms
  └──────────┬──────────┘
             │
      ┌──────┴───────┐
      │  >= 5 ?      │
      └──────┬───────┘
        是   │   否
      ┌──────▼──────┐   ┌──────────────────────────────┐
      │ 直接 429     │   │ Dubbo 查用户                 │
      │ 密码不校验    │   │ 用户不存在 → 计数+1 → 401     │
      └─────────────┘   │ 状态禁用   → 403（不计数）     │
                        │ BCrypt 校验                   │
                        │   失败 → 计数+1 → 401         │
                        │   成功 → DEL 计数 → 签 token   │
                        └──────────────────────────────┘
```

### 为什么检查放在最前面

| 操作 | 耗时 | 被刷 1000 次/秒的成本 |
|---|---|---|
| Redis GET | 0.3 ms | 0.3 核 |
| Dubbo + MySQL | 5~10 ms | 5~10 核 |
| **BCrypt(cost=10)** | **60~80 ms** | **60~80 核（必然打满）** |

登录接口是**CPU 密集型**的，被锁定的人必须在花 70ms 之前就被挡住。

## 4. 实测行为

| 场景 | Redis `auth:fail:admin` | 响应 |
|---|---|---|
| 首次登录成功 | 不存在 | `code=0` |
| 密码错 1 次 | `1` | `401 账号或密码错误` |
| 密码错 5 次 | `5` | `401 账号或密码错误` |
| **第 6 次，密码正确** | `5`（不变） | **`429 失败次数过多，请 15 分钟后再试`** |
| 15 分钟后 | 自动消失 | 恢复正常 |
| 手动 `DEL` 后 | 不存在 | 立即恢复正常 |

**注意 HTTP 状态码**：业务异常由全局处理器包装，返回的是 **HTTP 200 + body.code=429**（Apifox 里"校验通过 200"但 body 是 429，就是这个原因）。

## 5. 设计取舍说明

| 决策 | 为什么这么定 | 代价 |
|---|---|---|
| **按账号计数**（不是按 IP） | 攻击者换 IP 很容易，换目标账号不容易 | 同一 IP 攻击大量账号时无效 |
| **锁定在校验密码之前** | 保护 CPU | 密码正确也进不去，用户体验差（文案要说清楚） |
| **账号不存在也计数** | 防账号枚举（响应文案完全一致） | 可被用来"恶意锁定他人账号"（DoS） |
| **固定窗口 15 分钟** | 实现简单 | 攻击者可在窗口切换点"卡点"多试几次 |
| **成功即清零** | 正常用户偶尔错一次不受影响 | 攻击者若偶尔猜中会重置计数（概率低） |

## 6. 当前实现的四个漏洞

### 6.1 大小写绕过（已实测确认）

```
DB 查账号：utf8mb4_general_ci，不区分大小写 → ADMIN 能查到 admin
Redis 计数：区分大小写 → auth:fail:ADMIN 是另一个 key
```

实测结果：

```
auth:fail:ADMIN → 1
auth:fail:admin → (nil)
```

攻击者用 `admin / Admin / ADMIN / aDmIn...` 可把 5 次变成 160 次。

**修法（一行）**：

```java
String account = request.getAccount().trim().toLowerCase(Locale.ROOT);
```

### 6.2 只按账号计，不管来源 IP

同一 IP 攻击 1 万个账号，每个错 1 次 → 账号维度全部未触发，但已经试了 1 万次（密码喷洒）。

**修法**：网关加 IP 维度限流（Redis 令牌桶或 Sentinel `GatewayFlowRule`）。

### 6.3 可被用来恶意锁定他人

知道对方账号，错 5 次就能锁他 15 分钟。

**修法**：
- 计数 key 同时带 IP：`auth:fail:{account}:{ip}`，锁定只在"同账号+同 IP"生效
- 或者锁定后仍允许走验证码通道登录

### 6.4 `INCR` + `EXPIRE` 非原子

两条命令之间进程崩溃 → key 永不过期 → 该账号被永久锁定。

**修法（Lua）**：

```lua
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return c
```

只对第一次设置过期，避免每次失败都把窗口"续期"（当前实现每次失败都会 `EXPIRE`，等于滑动窗口——这其实是更好的行为，但要明确是有意为之）。

## 7. 加固路线（按优先级）

### P0（半天内可做）

| 项 | 做法 | 收益 |
|---|---|---|
| 账号归一化 | `toLowerCase(Locale.ROOT)` | 堵住大小写绕过 |
| 失败日志 | 超限时 `log.warn("账号被锁定 account={}")` | 可观测，便于发现撞库 |
| Lua 原子计数 | 见 6.4 | 防永久锁定 |

### P1（1~2 天）

| 项 | 做法 | 收益 |
|---|---|---|
| IP 维度限流 | 网关按 IP 计数：`rl:login:{ip}`，10 次/分钟 | 防密码喷洒 |
| 渐进式延迟 | 第 3 次失败后 `sleep(200ms * (n-2))` | 拖慢脚本，对真人无感 |
| 验证码 | 错 3 次后必须图形验证码 | 打断自动化 |

### P2（一周）

| 项 | 做法 | 收益 |
|---|---|---|
| 设备指纹 | 客户端上报 `deviceId` + 首次登录校验 | 识别批量脚本 |
| 异地/异常登录检测 | 登录时比对历史 IP 城市、UA | 账号被盗告警 |
| 指标告警 | 每分钟失败数、锁定账号数、429 比例 | 及早发现攻击 |
| 滑动窗口 | 用 ZSET 记录失败时间戳，窗口内计数 | 比固定窗口更公平 |

## 9. 与网关限流的分工

| 层 | 维度 | 防什么 | 现状 |
|---|---|---|---|
| **auth（当前）** | 账号 | 单账号暴力破解 | ✅ 已实现 |
| gateway（规划） | IP / 用户 | 密码喷洒、批量撞库 | ❌ 未实现 |
| ws-gateway（规划） | 连接数 / 消息速率 | 消息洪泛 | ❌ 未实现 |

**两层都要有**：只有账号维度 → 换账号就绕过；只有 IP 维度 → 换 IP 就绕过。

---

## 10. 一句话总结

> **防撞库的本质是"用最便宜的操作，挡住最贵的操作"**：先花 0.3ms 查一次 Redis 计数，把 70ms 的 BCrypt 保护起来；阈值一到直接 429，让攻击者的每次尝试都拿不到任何信息（连"密码对不对"都不告诉他）。
