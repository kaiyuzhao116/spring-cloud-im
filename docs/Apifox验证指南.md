# 用 Apifox 验证登录链路

> 配套文件：`docs/apifox/spring-cloud-verify.postman_collection.json`（可直接导入 Apifox）
> 相关文档：[启动与运行指南](启动与运行指南.md) · [手动验证与调试指南](手动验证与调试指南.md)

> ⚠️ **2026-10-22 变更**：token 精简为 `sub / iat / exp`，登录响应不再返回 `sessionId`，
> 网关不再校验 `ver`，`logout` 变为空实现。文中涉及 `ver` / `sess` 的实验已标注"需先恢复字段"。

Apifox 相比 `curl` 的好处：请求能存下来反复点、能自动提取 token、能写断言、能留响应示例、团队可共享。学这条链路用它最省事。

---

## 1. 导入集合

### 1.1 步骤

1. 打开 Apifox → 进入（或新建）一个项目
2. 顶部 `项目设置` 左侧 → **导入数据**
3. 选择 **Postman** → 上传文件
4. 选 `docs/apifox/spring-cloud-verify.postman_collection.json`
5. 导入方式选「**新建目录**」，确认

> 也可以直接把该 json 文件**拖进** Apifox 窗口。

### 1.2 导入后应看到 4 个目录 / 15 个接口

```
spring_cloud 登录链路验证
├── 01 依赖健康（L0）                    3 个
├── 02 直连服务（L1，绕过网关）           3 个
├── 03 走网关（L2/L3）                    6 个
└── 04 失败路径（L5）                     3 个
```

### 1.3 检查集合变量

点集合名 → `变量`，确认这几个值（默认已经是本机端口）：

| 变量 | 值 | 说明 |
|---|---|---|
| `gateway` | `http://127.0.0.1:8080` | 网关 |
| `authDirect` | `http://127.0.0.1:8083` | 直连 auth |
| `userDirect` | `http://127.0.0.1:8084` | 直连 user |
| `nacos` | `http://127.0.0.1:8848` | Nacos |
| `token` | 空 | 登录后自动写入 |
| `sid` | 空 | 登录后自动写入 |

**用 `127.0.0.1` 而不是 `localhost`**：某些环境 `localhost` 会优先解析成 IPv6 `::1`，而 Nacos/服务监听在 IPv4，会出现"端口能连但请求失败"的怪现象。

### 1.4 变量没生效怎么办（必看）

**现象**：请求报

```
请求发生错误
Invalid URL "http://nacos/v1/ns/service/list?pageNo=1&pageSize=20&namespaceId=public"
```

**原因**：集合里的 `{{nacos}}` 没有被替换，Apifox 把它当成了普通域名 `nacos`，自动补成 `http://nacos/...`。
Postman 的**集合变量**导入 Apifox 后不一定参与解析，最稳妥的是用**环境变量**。

**做法（二选一）**：

方案 A（推荐）：导入环境文件

1. `项目设置` → `导入数据` → Postman → 选 `docs/apifox/local.postman_environment.json`
2. 右上角环境下拉选择 **spring_cloud 本地环境**
3. 再发一次请求，URL 会变成 `http://127.0.0.1:8848/...`

方案 B：手动建环境

1. 右上角环境管理 → 新建环境 `本地`
2. 添加变量：`gateway`=`http://127.0.0.1:8080`、`authDirect`=`http://127.0.0.1:8083`、`userDirect`=`http://127.0.0.1:8084`、`nacos`=`http://127.0.0.1:8848`
3. 选中该环境后再发请求

方案 C（最快验证用）：直接把 URL 写死，比如 `http://127.0.0.1:8848/nacos/v1/ns/service/list?pageNo=1&pageSize=20&namespaceId=public`。

**判断变量是否生效**：URL 输入框里 `{{nacos}}` 应显示为高亮的变量块（悬停能看到值）；如果变成纯文本 `nacos`，就是没解析。

## 2. 按顺序点：先直连，后网关

这个顺序是刻意设计的，**先证明服务本身对，再证明网关对**。出错时能立刻知道是哪一层。

### 第一轮：01 依赖健康（3 个）

| 接口 | 看什么 | 预期 |
|---|---|---|
| Nacos 服务列表 | `count` 和 `doms` | `count=3`，含 `user` `auth` `api-gateway` |
| 网关健康 | `status` | `UP` |
| user 健康 | `status` | `UP` |

**如果第一个就失败**：Nacos 没起，或服务没注册。先解决这个，后面全白搭。

### 第二轮：02 直连服务（3 个）

| 接口 | 关键点 | 预期 |
|---|---|---|
| 直连 auth 登录 | URL 是 **`/login`**，没有 `/api/auth` 前缀 | `code=0`，Body 里有 `accessToken`（精简版已无 `sessionId`） |
| 直连 user + 手工 `X-User-Id: 1` | user 完全不看 token | 返回 `admin / 管理员` |
| 直连 user 不带身份头 | 对比上一条 | `401`，message 是 **`缺少身份信息，请通过网关访问`** |

**这三条是理解整套设计的钥匙**：user 只信请求头里的 `X-User-Id`，所以必须有网关注入——这就是网关存在的理由。

> 直连这条会把 `token` 变量覆盖成"直连拿到的 token"，没关系，下一轮会重新登录。

### 第三轮：03 走网关（6 个，核心）

| 顺序 | 接口 | 预期 | 看什么 |
|---|---|---|---|
| 1 | 网关登录 | `code=0` | 后置脚本自动把 `accessToken` 存进环境变量 `token` |
| 2 | 带 token 拉资料 | `code=0`，`nickname=管理员` | 身份是网关从 token 的 `sub` 解出来注入的 |
| 3 | 无 token | `401 未登录或登录已失效` | 网关第一道门（白名单之外一律拦） |
| 4 | 伪造 token（`abc.def.ghi`） | `401 登录已失效，请重新登录` | 验签失败 |
| 5 | 伪造头 + 无 token | `401` | **只加 `X-User-Id` 骗不过网关** |
| 6 | 退出登录 | `code=0` | 精简版是空实现，服务端不做任何事 |

**注意第 3、4 条的 message 不同**：

- `未登录或登录已失效` → 没带 Authorization 头
- `登录已失效，请重新登录` → 带了但验签失败

**这两个文案的差异就是排错线索**，不要以为一样。

> 精简版只有这两种 401。原先的第三种 `凭证已失效，请重新登录`（`ver` 对不上）
> 需要 token 里有 `ver` 字段才会出现，见 [系统设计与实现](系统设计与实现.md) 5.3 的恢复步骤。

### 第四轮：04 失败路径（3 个）

| 接口 | 预期 | 说明 |
|---|---|---|
| 密码错误 | `401 账号或密码错误` | 同时 Redis 里 `auth:fail:admin` 会 +1 |
| 账号不存在 | `401 账号或密码错误`（**完全相同**） | 防账号枚举 |
| 参数为空 | `400 账号不能为空` | `@Valid` 生效 |

⚠️ 密码错误那个连点 5 次，`admin` 会被锁 15 分钟（即使密码正确也进不去）。解锁：

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 del "auth:fail:admin"
```

## 3. Apifox 做不了的部分：失效实验要配合终端

> ⚠️ **2026-10-22 起 token 精简为 `sub / iat / exp`**，会话写入与版本号校验已从代码移除。
> 本节 3.1 / 3.2 的实验**当前不会生效**（`INCR ver` 没有代码去比对，`DEL sess` 也没有代码去读）。
> 想重做这两个实验，先按 [系统设计与实现](系统设计与实现.md) 5.3 把 `sid` / `ver` 加回来。

"踢人立即生效"这类实验要改 Redis，Apifox 发不了 Redis 命令。**保留一个 PowerShell 窗口**执行：

### 3.1 全端踢人 → 观察 token 立即失效（需先恢复 ver 字段）

```powershell
# 1) 先在 Apifox 点「网关登录」，确认 token 变量有值
# 2) 终端执行：版本号 +1
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 incr "auth:user:1:ver"
# 3) 回 Apifox 点「带 token 拉资料」
```

预期（恢复 ver 之后）：`{"code":401,"message":"凭证已失效，请重新登录"}`

**恢复**：再点一次「网关登录」（新 token 带 `ver=1`），然后第 2 条接口恢复正常。

### 3.2 踢单台设备 → 观察"30 分钟窗口"（需先恢复 sid）

> 精简版没有 `auth:sess:{sid}` 可删，此实验同样需要先把会话写入加回来。

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 del "auth:sess:<Apifox 里 sid 变量的值>"
```

预期：**仍然返回 200**。

**这就是当前设计的已知限制**：方案 A 没有 `revoked` 黑名单，网关只比对 `ver`，不看会话是否存在。这个实验能让你彻底理解"为什么需要第三个 key"。

### 3.3 看 Redis 里到底存了什么

```powershell
$cli = "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe"
& $cli -p 6379 keys "auth:*"
& $cli -p 6379 hgetall "auth:sess:<sid>"
& $cli -p 6379 get "auth:user:1:ver"
& $cli -p 6379 get "auth:fail:admin"
```

## 4. Apifox 的四个进阶用法（学完基础再玩）

| 用法 | 怎么做 | 用途 |
|---|---|---|
| **环境切换** | 右上角环境管理，建 `本地` / `测试`，把 `gateway` 等变量放环境里 | 换机器/换端口不用改接口 |
| **保存响应示例** | 请求成功后点「保存为示例」 | 形成接口文档，前端照着对接 |
| **前置脚本** | 请求 → 前置操作 → 自定义脚本，可 `pm.sendRequest` | 例如每次先自动登录拿 token |
| **自动化测试** | 目录右键 → 「运行」/ 测试场景 | 一次跑完 15 个接口，出报告 |

### 4.1 断言在 Apifox 里怎么生效

导入的集合里带了 Postman 风格的断言脚本：

```javascript
pm.test('code=0', function () {
    pm.expect(pm.response.json().code).to.eql(0);
});
```

Apifox 兼容 `pm.test` / `pm.expect` / `pm.response.json()`。**如果某个断言不生效**，换成 Apifox 原生写法：

`请求 → 后置操作 → 添加断言 → 选择 JSON 提取 → 表达式 $.code 等于 0`

### 4.2 token 自动传递（导入后可能要确认）

「网关登录」的后置脚本里有：

```javascript
pm.collectionVariables.set('token', pm.response.json().data.accessToken);
```

如果导入后变量没更新，改成 Apifox 原生：`后置操作 → 提取变量 → 变量名 token → JSONPath: $.data.accessToken`。

## 5. 排错对照（Apifox 里看到什么 → 说明什么）

| Apifox 现象 | 原因 | 处理 |
|---|---|---|
| `Could not send request` / `ECONNREFUSED` | 对应端口没起 | 按启动顺序检查端口 |
| 所有接口 404 | 变量 `gateway` 少了 `http://` 或写错端口 | 检查集合变量 |
| 直连 auth 报 404 | 用了 `/api/auth/login` | 直连时路径是 `/login` |
| 401 `未登录或登录已失效` | 没带 Authorization，或 token 变量为空 | 先跑「网关登录」 |
| 401 `登录已失效，请重新登录` | token 被改坏/密钥不一致 | 重新登录；检查两端 `jwt.secret` |
| 401 `凭证已失效，请重新登录` | `ver` 对不上（被 INCR 过）——**精简版不会出现** | 重新登录即可 |
| 401 `缺少身份信息，请通过网关访问` | 直连了 user 却没带 `X-User-Id` | 加头，或改走网关 |
| 500 `系统繁忙` | MySQL 未运行 / Dubbo 找不到 user | 看 auth 与 user 日志 |
| 429 | 密码错 5 次被锁 | `redis-cli del auth:fail:admin` |
| 变量显示成 `{{token}}` 没替换 | 变量没定义在集合/环境里 | 补变量 |
| `Invalid URL "http://nacos/..."` | `{{nacos}}` 没解析，被当成域名 | 导入环境文件并选中环境（见 1.4） |
| URL 变成 `http://127.0.0.1:4523/m1/...`，响应是 `{}` | 当前环境是 **`本地 Mock`**，Mock 环境中所有请求都被改写到 Mock 服务器 | 右上角切换成真实环境（`spring_cloud 本地环境` 或自建"本地"），**Mock 环境永远打不到真实服务** |
| 断言一直显示"未通过" | 导入的 `pm.test` 未生效 | 改用 Apifox 原生后置断言 |

## 7. 怎么验证才能"记住"，而不是"看过"

**核心原理：记忆来自"预测被打破"，不来自"看到正确答案"。**

看到 401 不会记住；**先猜 401、结果拿到 200**，然后想明白为什么，才会真正记住。所以下面每个实验都必须先写字、再点发送。

### 7.1 三步法（每点一个接口都这么干）

1. **预测**（先别看结果）：写下来 `code=? message=? Redis 会多什么 key?`
2. **验证**：Apifox 点发送，把实际结果写在同一行
3. **解释偏差**：不一样的地方，必须能用一句话说清原因。**说不出来就是没懂**，回去看对应代码。

### 7.2 六个必做对照实验（每个 3 分钟）

| # | 实验 | 具体操作 | 先写下你的预测 | 真正要记住的 |
|---|---|---|---|---|
| 1 | 直连 user 带 vs 不带头 | 02 目录两个接口对比 | 分别什么状态码、message 各是什么 | user **完全不信 token**，只信 `X-User-Id` |
| 2 | 两种 401 的区别 | 03 目录：无 token / 伪造 token | 两条 message 分别是什么 | 两个拦截点：没带票 / 假票（第三种"票作废"需恢复 `ver`） |
| 3 | StripPrefix 方向 | 把 `AuthController` 改成 `@PostMapping("/api/auth/login")`，重启 auth | 经网关会怎样？直连呢？ | 网关剥前缀，Controller 写剥完的路径 |
| 4 | 锁定优先级 | 密码错 5 次后，用**正确密码**登录 | 能进吗？为什么？ | 失败计数在密码校验**之前**，且高于密码正确 |
| 5 | 两种踢人的差别（需先恢复字段） | `INCR ver` 后请求；再登录后 `DEL sess` 再请求 | 哪个立即 401？哪个仍 200？ | `ver` 是每请求对账，`sess` 网关不看 → 30 分钟窗口 |
| 6 | 密钥必须一致 | 网关 `gateway.auth.secret` 加一个字符，重启网关 | 带有效 token 会返回什么？ | 验签是共享密钥，改一端全站 401 |

> 实验 3、6 改完记得**改回去并重启**，否则后面全乱。

### 7.3 记录模板（照着填，一周后回看）

### 7.4 费曼测试：用 3 句话讲清楚

能说出下面三句，说明真的懂了：

1. **为什么 user 不解析 token？** —— 因为所有请求都过网关，网关统一验签并注入身份，下游只做业务，避免每个服务重复实现鉴权。
2. **为什么需要 `sid` 和 `ver` 两个东西？** —— `sid` 用来精确定位"哪一次登录"，`ver` 用来一次性作废"这个人的全部登录"，一个管点、一个管面。
3. **为什么踢单台设备有 30 分钟窗口？** —— 因为网关只对账 `ver` 不看会话，token 自身还有效期；要堵住就得再加 `revoked` 黑名单。

### 7.5 反向重建（最有效的一步）

关掉代码，在纸上（或 Apifox 的 Markdown 笔记里）画出这条链路：

```
浏览器 → 网关 → auth → Dubbo → user → MySQL
                  ↘ Redis(2 个 key)
```

标出**每一步的输入输出**和**可能失败的位置**，再打开代码对照。画不出来的地方，就是你还没掌握的地方。
