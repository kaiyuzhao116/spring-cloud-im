# 消息链路全流程与限制

> 一条消息从手机到另一个手机，经过哪些环节、每道闸拦什么、出错会怎样。
> 适用于排查"消息发不出去 / 对方收不到 / 重复 / 乱序"这类问题。

---

## 0. 先记住两句话

**业务上就两件事：**

```
① 存（可靠性）→ seq、幂等、事务、ACK、MQ 事件
② 送（实时性）→ 连接表、MQ 广播、isWritable、离线拉取
```

**防御上也就两件事：**

```
① 入站限大小（64KB / 4KB / 2000 字符）→ 防止被一条消息撑爆
② 出站限积压（isWritable 64KB）        → 防止被慢客户端拖死
```

---

## 1. 全景

```
小明手机                 ws-gateway(Netty)              im                    RabbitMQ           小红手机
   │                          │                         │                       │                 │
   │ ①MSG 帧                 │                         │                       │                 │
   ├─────────────────────────▶│ ②限大小+认人+切线程     │                       │                 │
   │                          │ ③Dubbo send             │                       │                 │
   │                          ├────────────────────────▶│ ④校验/幂等/seq/事务   │                 │
   │                          │                         │ ⑤提交后发事件          │                 │
   │                          │◀────────────────────────┤                       │                 │
   │ ⑥ACK                    │                         ├──────────────────────▶│                 │
   │◀─────────────────────────┤                         │                       │ ⑦广播到各实例    │
   │                          │◀────────────────────────────────────────────────┤                 │
   │                          ├──────────────────────────────────────────────────────────────────▶│
```

**关键分界：④ 的事务提交 = 消息"存住了"；⑥ ACK 只汇报这一件事，与 ⑦ 无关。**

## 2. 一次发送的完整流程（含全部闸门）

示例：uid=1（小明）→ uid=2（小红），内容「在吗」，cid=`c-8f3a`，seq=26。

### 阶段一：建连（前置）

| # | 步骤 | 本条的值 | 闸门 | 超限表现 |
|---|---|---|---|---|
| 1 | 连接 `/ws?token=xxx` | 路径 `/ws` | 路径必须 `/ws` | 404 |
| 2 | 握手验签 | token 有效（还有 28 分钟） | 必须有效未过期 | 401，拒连 |
| 3 | 写身份 | `USER_ID=1`、`CONNECT_TIME` | — | — |
| 4 | 登记连接 | `connId`，本机连接数 +1 | — | — |

### 阶段二：前端发送

| # | 步骤 | 本条的值 | 闸门 | 超限表现 |
|---|---|---|---|---|
| 5 | 按回车 | 内容非空、已连接 | 前端校验 | 不发，界面提示 |
| 6 | `ws.send(json)` | 47 字节 | 浏览器无限制 | 交给服务端拦 |

### 阶段三：Netty 接入（闸门最密）

| # | 步骤 | 本条的值 | 闸门 | 超限表现 |
|---|---|---|---|---|
| 7 | 收到字节 | 47 字节 | **单帧 ≤ 64KB** | 1006，断 |
| 8 | 解帧（去掩码） | `TextWebSocketFrame` | — | — |
| 9 | 重置空闲计时 | 距上次 3 秒 | **60 秒无数据踢人** | 1006 |
| 10 | **字节数检查** | **47 字节** | **≤ 4096** | **1009**，断 + 日志 bytes |
| 11 | JSON 解析 | 合法 | 必须合法 | 丢弃（不断开） |
| 12 | 类型判断 | `MSG` | 只认 MSG/PING | 忽略（不断开） |
| 13 | 字段校验 | to/cid/content 均非空 | 必须齐全 | 丢弃（不断开） |
| 14 | 取身份 | `fromUid=1`（来自 attr） | 必须有值 | 关连接 |
| 15 | 丢线程池 | 队列当前 3 个 | **8 线程 / 队列 5000** | 背压（CallerRuns） |

### 阶段四：Dubbo → im

| # | 步骤 | 本条的值 | 闸门 | 超限表现 |
|---|---|---|---|---|
| 16 | Dubbo 调用 | 2ms | **超时 3000ms、不重试** | 异常 → ACK `seq=0` |

### 阶段五：im 落库

| # | 步骤 | 本条的值 | 闸门 | 超限表现 |
|---|---|---|---|---|
| 17 | 参数校验 | to=2、cid 6 字符、内容 2 字符 | `to>0`、`cid≤64`、**`content≤2000 字符`** | BizException → ACK `seq=0` |
| 18 | 算会话 | `s_1_2` | — | — |
| 19 | 幂等查询 | 查不到 `(from=1, cid=c-8f3a)` | `uk_client` 唯一 | 命中 → 返回旧结果 |
| 20 | 取 seq | `INCR im:seq:s_1_2` → 26 | Redis 可用 | 异常 → ACK `seq=0` |
| 21 | 写消息 | 1 行 `im_message` | `uk_conv_seq` 唯一 | 冲突 → 重试/失败 |
| 22 | 写会话卡片 | 2 行 `im_conversation_member` | — | 失败则整体回滚 |
| 23 | 列宽 | 6 字节 | `varchar(2000)` | 报错（已被 17 提前拦） |
| 24 | **提交事务** | — | 三条全成功 | 回滚 → ACK `seq=0` |

### 阶段六：两条回程（并行）

**线 A：MQ 事件**

| # | 步骤 | 闸门 | 超限表现 |
|---|---|---|---|
| 25 | `afterCommit` → `im.events` | broker 可写 | 只记日志，不影响 ACK |
| 26 | 投递到各实例匿名队列 | 队列已绑定 | 相应实例收不到 |

**线 B：ACK 回发送方**

| # | 步骤 | 闸门 | 超限表现 |
|---|---|---|---|
| 27 | Dubbo 返回 `{msgId, seq}` | — | — |
| 28 | `send(ctx, ack)` | `channel.isActive()` | 静默不写（消息仍在库） |
| 29 | 前端处理 ACK | `seq===0` 视为失败 | 红色"发送失败" |

**线 C：推给接收方**

| # | 步骤 | 闸门 | 超限表现 |
|---|---|---|---|
| 30 | 消费 MQ 事件 | 异常需自吞（避免重投） | 丢推送 |
| 31 | 查本机连接 `userChannels[toUid]` | 用户可能不在本机 | `命中连接数=0`，丢弃 |
| 32 | `isActive()` | 连接可能已断 | 丢弃 |
| 33 | **`isWritable()`（水位 64KB）** | 缓冲可能已满 | 丢弃 |
| 34 | 写帧 → 客户端渲染 | — | — |

## 3. 闸门汇总表

| 层 | 限制 | 值 | 超限后果 | 客户端看到 |
|---|---|---|---|---|
| 握手 | token 有效期 | 30 分钟 | 拒绝连接 | 401 |
| 协议 | 单帧大小 | **64KB** | 断连接 | 1006 |
| 业务 | 单帧大小 | **4KB** | 断连接 + 日志 bytes | **1009** |
| 业务 | JSON / 字段 | 必须合法 | 丢弃，不断开 | 无（消息静默丢失） |
| 线程 | 线程数 | 8 | 排队 | 延迟变大 |
| 线程 | 队列 | **5000** | CallerRuns 背压 | 整体变慢 |
| RPC | 超时 | 3 秒 | 抛异常 | ACK `seq=0` → 失败 |
| 业务 | 内容长度 | **2000 字符** | BizException | ACK `seq=0` → 失败 |
| 业务 | 幂等 | cid 唯一 | 返回旧结果 | 正常 ACK（不新增） |
| 存储 | 唯一键 | conv+seq | 冲突重试/失败 | 可能失败 |
| 存储 | 列宽 | varchar(2000) | 报错 | 失败 |
| 出站 | 发送缓冲 | **64KB/连接** | 丢推送 | 收不到（可拉取） |
| 空闲 | 无数据时长 | **60 秒** | 断连接 | 1006 |

**放置原则：越早拦越便宜，越靠外越硬（协议层直接断，业务层给原因）。**

## 4. 数据在内存里的旅程

```
① 网卡 → 内核 socket 接收缓冲
② Netty 逐块读入 → 堆外 ByteBuf（累积成一帧，≤64KB）
③ frame.text() → 堆内 String（UTF-16，中文 2 字节/字符）
④ Jackson 解析 → 堆内 Frame 对象 + 各字段 String
⑤ 丢进 bizExecutor 队列（Runnable 持有 Frame，GC 收不走）
⑥ Dubbo 序列化（hessian2）→ 字节 → im 反序列化 → 又一份对象
⑦ JDBC 编码 → 字节 → TCP 发给 MySQL（3306）
⑧ MySQL：写 redo log + buffer pool → COMMIT 时 fsync 磁盘
```

**同一份「在吗」在内存里被复制 4~5 次**（UTF-8 字节 → UTF-16 字符 → 对象 → 序列化字节 → 驱动字节）。

## 5. 内存风险与对应防护

| 风险 | 谁持有 | GC 能回收吗 | 防护 |
|---|---|---|---|
| 入站单帧过大 | 堆外 ByteBuf | ❌（靠 release） | 64KB 协议闸 |
| 队列堆积 | `bizExecutor` 队列 | ❌（被引用） | 4KB 业务闸 + 队列 5000（最坏 ~20MB） |
| 出站缓冲堆积 | Netty 写缓冲（堆外） | ❌ | `isWritable()` 64KB 水位，超了丢弃 |
| 僵尸连接 | `ChannelManager` | ❌ | `IdleStateHandler` 60 秒 |
| 堆外泄漏 | 忘记 release | ❌ | `SimpleChannelInboundHandler` 自动 release |

**最坏占用估算（当前配置）**

```
队列：5000 × 4KB ≈ 20MB
单连接出站：≤ 64KB
单帧入站：≤ 64KB
```

## 6. 各阶段"算不算已存"

| 阶段 | 存在哪 | 进程崩溃会丢吗 | 算已存 |
|---|---|---|---|
| 浏览器 | 发送缓冲 | 丢 | ❌ |
| Netty 堆外 | ByteBuf | 丢 | ❌ |
| **线程池队列** | 堆内 Runnable | **丢** | **❌** |
| im 内存 | 局部变量 | 丢 | ❌ |
| **MySQL 提交后** | **磁盘** | **不丢** | **✅** |
| RabbitMQ | broker | 取决于持久化配置 | 只是通知 |

**"入队 ≠ 存储"。进程在入队后崩溃时，客户端没收到 ACK，会用同一个 cid 重发，靠幂等保证不重复。**

## 7. 失败场景对照

| 失败点 | 发送方看到 | 接收方看到 | 消息丢了吗 |
|---|---|---|---|
| 超 64KB | 1006 断开 | 无 | 未产生 |
| 超 4KB | 1009 断开 | 无 | 未产生 |
| JSON/字段非法 | 无（静默丢弃） | 无 | 未产生 |
| Dubbo 超时 / im 异常 | ACK `seq=0` → "发送失败" | 无 | 未产生 |
| 事务回滚 | ACK `seq=0` | 无 | 未产生 |
| MQ 发送失败 | **正常 ACK** | 收不到实时推送 | 不丢（在库） |
| 接收方离线 | 正常 ACK | 无 | 不丢（在库） |
| 接收方缓冲满 | 正常 ACK | 缺这条 | 不丢（在库） |
| 服务端进程崩溃（已 ACK） | — | 可能收不到 | 不丢（在库） |

**规律：存失败 → 报错；送失败 → 静默，靠拉取补偿。**

## 8. 当前缺口

| 缺口 | 攻击/风险 | 后果 | 建议 |
|---|---|---|---|
| **无频率限制** | 一个合法连接每秒发 100 条 | im/MySQL 被打满，全员变慢 | 每连接令牌桶（如 10 条/秒） |
| **无每 IP 连接上限** | 单机开数千连接 | 占满文件句柄与内存 | `channelActive` 里按 IP 计数 |
| **无总连接数上限** | 分布式灌连接 | 握手耗 CPU | 全局计数器 + 超限拒绝 |
| **不处理分片帧** | 分片消息 | `ContinuationWebSocketFrame` 被静默丢弃 | 显式拒绝或聚合 |
| 阈值口径不一致 | 4KB 按字节、2000 按字符 | 英文长文报错原因不清晰 | 统一为字符数 + 字节做内存保护 |
| ~~无历史消息接口~~ | — | 已实现 `/messages`、`/conversations`、`/read` | ✅ |
| ~~单端登录~~ | — | 已实现 4001 + Redis 在线表 + MQ 广播（见第 12 节） | ✅ |

## 9. 排查口诀

| 现象 | 先看哪里 |
|---|---|
| 连不上（`server rejected`） | 握手验签：token 是否过期、8089 是否启动 |
| 连上但发消息无反应 | ws-gateway 日志有无 `帧过大 / 解析失败 / 调用 im 失败` |
| 显示"发送失败" | im 是否启动、Nacos 里 im 实例 IP 是否正确 |
| 消息发出但对方收不到 | RabbitMQ 是否运行；日志 `命中连接数=0` 说明对方离线 |
| 消息有重复 | 客户端是否重发；`client_msg_id` 是否每次都新生成 |
| 顺序乱 | 是否按 `seq` 排序（不要用 `created_at`） |
| 服务周期性卡顿 | 是否有 Full GC；队列深度是否持续增长 |
| 内存持续上涨但堆正常 | 堆外：出站缓冲堆积或 ByteBuf 未释放 |

## 10. 分层与扩展

### 10.1 三层阈值，各管一段

| 层 | 阈值 | 位置 | 回答的问题 |
|---|---|---|---|
| 协议层 | **64KB/帧** | `netty.max-frame-length` | 这条连接会不会被撑爆？ |
| 业务层 | **4KB/帧（文本）** | `BusinessHandler` 第 37 行 | 这条消息合不合理？ |
| 存储层 | **2000 字符** | `im` 的 `validate` + `varchar(2000)` | 数据库放不放得下？ |

**推荐比例：协议层 ≈ 业务层 × 2**（如 8KB / 4KB）。相等会让"稍微超一点"也变成无法解释的 1006；过宽（64KB）又会让 60KB 的垃圾帧白传一遍。

### 10.2 要不要把协议层也设成 4KB

**不建议。阈值不一致有六个好处：**

| # | 好处 | 说明 |
|---|---|---|
| 1 | 能说清原因 | 4~64KB 走业务层，能回 1009 + 日志 `bytes=` |
| 2 | 故障定位分明 | 1009 = 业务拒绝；1006 = 协议硬断 |
| 3 | 业务可单独调整 | 产品放宽到 8KB，只改一个常量 |
| 4 | 省带宽 | 明显异常的帧（声明 100MB）读到帧头就断，不用传完 |
| 5 | 职责清晰 | 协议层只保安全，业务层只定规范 |
| 6 | 留扩展空间 | 新帧类型（文件/位置）不用动安全参数 |

### 10.3 新增业务类型怎么加（不动协议层）

每种帧类型配自己的业务上限：

| 帧类型 | 业务上限 | 理由 |
|---|---|---|
| `MSG`（文本） | 4KB | 一篇短文 |
| `FILE`（文件消息） | 512B | 只有 fileId + 文件名 + 大小 |
| `LOC`（位置） | 200B | 经纬度 + 地址 |
| `PING` / `PONG` | 0 | 空帧 |

```java
switch (type) {
    case MSG  -> checkSize(frame, 4096);
    case FILE -> checkSize(frame, 512);
    case LOC  -> checkSize(frame, 200);
    case PING -> send(ctx, Frame.pong());
}
```

**新增一种业务 = 加一个 `case` + 一个上限常量，协议参数一行不改。**

### 10.4 大文件为什么不能走 WS

**正确做法：内容走 HTTP，WS 只传指针。**

```
① 客户端 HTTP POST /api/im/upload（或直传对象存储，预签名 URL）
② 服务端返回 fileId / url（几十字节）
③ WS 发一条小消息：{"type":"MSG","content":"[文件] 报告.pdf","fileId":"f_123"}
④ 对方点开时，自己用 HTTP 下载
```

| 对比 | WS | HTTP |
|---|---|---|
| 断点续传 | ❌ | ✅ Range |
| 失败重试 | 整条重传 | 按块重传 |
| 限流 / CDN | ❌ | ✅ |
| 背压 | 易堆积（写缓冲） | 天然流式 |
| 长连接占用 | 传输期间独占 | 互不影响 |

**什么情况下才该改协议层**：只有"决定让二进制大块数据也走 WS"时才需要——而这等于拆掉所有内存保护（单帧占 50MB、慢客户端传几分钟、断线重传成本极高）。

### 10.5 加新业务前的自检

- [ ] 这条帧最大多少字节？写进 case 常量
- [ ] 超过上限回什么？（1009 / ACK `seq=0` / 自定义 close 码）
- [ ] 内容需要落库吗？字段长度与 `varchar` 是否匹配
- [ ] 大内容是否应改走 HTTP / 对象存储
- [ ] 是否需要新的 `CLOSE_REASON`（便于排查）
- [ ] 前端是否需要新的状态文案

## 11. 读路径：历史 / 会话 / 未读 / 已读

发出去的消息最终要能被"读回来"。读路径一共三个入口：

| 接口 | 解决什么 | 关键参数 |
|---|---|---|
| `GET /messages` | 打开会话时的历史、断线后的补缺 | `beforeSeq`（往前翻）/ `afterSeq`（往后补） |
| `GET /conversations` | 左侧会话列表 + 未读红点 | — |
| `POST /read` | 消掉未读红点 | `{"conv","seq"}` |

### 11.1 补缺口（离线消息的正解）

```
断线期间的消息 → 不靠推送补（推不到）→ 靠客户端上报进度拉回来
   ↓
客户端记住本地最大 seq（如 43）
   ↓ 重连成功
GET /messages?conv=s_1_2&afterSeq=43
   ↓ 返回 44~50
追加到列表
```

**前端只在"重连"时补，首次连接靠首次加载**，否则会请求两遍。

### 11.2 未读 = 减法

```sql
unread = last_seq - last_read_seq
```

| 动作 | 对数据库的影响 |
|---|---|
| 对方发一条 | `last_seq + 1` → 未读自然 +1 |
| 我打开会话 | `last_read_seq = GREATEST(last_read_seq, 最新 seq)` → 未读归零 |

**不存 `unread` 字段**：存了就要维护，一旦某次漏加/多加就永久错位；减法永远自洽。

### 11.3 三个易错点

| 点 | 错误做法 | 后果 |
|---|---|---|
| 已读回退 | `SET last_read_seq = ?` | 乱序上报会把已读退回去，红点又冒出来 |
| 越权 | 不校验 conv 归属 | 改个参数就能读别人聊天记录 |
| 分页合并 | 直接 `push` | 历史 + 实时重叠 → 同一条出现两次 |

## 12. 单端登录与在线表

### 12.1 一句话机制

```
新连接握手 → 广播 kick 事件 → 所有实例各自踢掉本机上该用户的旧连接（4001）
```

**为什么广播**：旧连接可能连在别的实例上，本机表里没有。

### 12.2 在线表 `ws:online:{uid}`

```
HASH：field = connId，value = 实例地址，TTL = 120 秒
```

| 动作 | 时机 | 命令 |
|---|---|---|
| 登记 | 握手成功 | `HSET` + `EXPIRE` |
| **续期** | **收到 PING（25 秒一次）** | `EXPIRE` |
| 移除 | 关闭连接 | `HDEL connId`（**不能 DEL key**） |

**三条铁律**：HASH 而非 String（多端）、HDEL 而非 DEL（不误删）、必须续期（否则被误判离线）。

### 12.3 三个必须处理的边界

| 边界 | 处理 |
|---|---|
| 踢到自己 | 排除 `excludeConnId` + 先踢后登记 |
| 事件乱序（秒级重连两次） | 只踢比 `newConnTime` 更早的连接 |
| 必须带 4001 | 否则客户端看到 1006 会重连，形成互踢循环 |

### 12.4 关闭码一览

| 码 | 含义 | 客户端 |
|---|---|---|
| 1006 | 异常断开 | 重连 |
| 1009 | 单帧超 4KB | 不重连 |
| 4001 | 同账号在别处登录 | 不重连 |
| 4002 | token 过期（未实现） | 不重连 |
| 4003 | 服务重启（未实现） | 退避重连 |
