# 手动验证与调试指南

> 目的：不是"跑通就行"，而是**通过一层层验证，把每个组件的作用看明白**。
> 每个实验都按「目的 → 操作 → 预期 → 说明了什么」写，做一遍就知道代码为什么这么写。
> 配套文档：[系统设计与实现](系统设计与实现.md) · [启动与运行指南](启动与运行指南.md)
> 不想敲命令：用 **[Apifox 验证指南](Apifox验证指南.md)**，导入集合后点着看。
>
> ⚠️ **2026-10-22 变更**：token 精简为 `sub / iat / exp`，会话写入与 `ver` 校验已从代码移除。
> 因此 **第 6 章（L4 失效机制）的两个实验当前不会生效**；想重做需要先按
> [系统设计与实现](系统设计与实现.md) 5.3 把 `sid` / `ver` 加回来。其余章节（L0~L3、L5）不受影响。

---

## 0. 先建立"分层验证"的意识

一个请求要穿过 6 层，任何一层都可能出问题。**从下往上验证，出问题时才能立刻定位**：

```
L0 中间件    Nacos / Redis / MySQL         ← 依赖是否活着
L1 服务本身  直连 8084 / 8083              ← 业务逻辑对不对
L2 网关路由  经 8080 转发                  ← StripPrefix、lb:// 是否生效
L3 身份传递  X-User-Id 注入与伪造头剥离     ← 过滤器是否在正确位置
L4 失效机制  ver / sess                    ← 会话与踢人是否真的生效
L5 失败路径  密码错 / 锁定 / 依赖挂掉       ← 异常处理是否友好
```

**核心原则：每层只改一个变量。** 同时改两个地方，出了问题就说不清是谁的锅。

```powershell
Get-NetTCPConnection -State Listen -LocalPort 8848,6379,3306,8080,8083,8084 |
  Select-Object LocalPort,OwningProcess | Sort-Object LocalPort
```

**要点：** 这里出现的名字必须和 Spring Cloud 的服务名（`spring.application.name`）一致，网关的 `lb://user` 才能找到它。

### 1.3 Redis

## 2. 启动顺序与日志解读

### 2.1 顺序

```
Nacos → Redis → MySQL → user(8084) → auth(8083) → api-gateway(8080) → web(5173)
```

为什么要按这个顺序：auth 启动时会初始化 Dubbo 消费者，user 没起会刷 `No provider available` 的警告（不致命，但日志很难看）。

### 2.2 日志里哪些行是"关键证据"

| 日志 | 说明什么 |
|---|---|
| `Tomcat started on port(s): 8084 (http)` | Web 容器起来了，端口可用 |
| `Started UserApplication in 19.279 seconds` | 应用启动完成，这才是"成功"的唯一标准 |
| `nacos registry, DEFAULT_GROUP user 172.24.160.1:8084 register finished` | 已注册到 Nacos，网关能发现它 |
| `Netty started on port 8080` | 网关（WebFlux）用的是 Netty，不是 Tomcat |
| `dubbo ... Export dubbo service ... to url dubbo://...:20882` | Dubbo 服务已对外暴露 |
| `APPLICATION FAILED TO START` | 启动失败，紧跟着的 `Description` 就是原因 |

**练习：** 把 user 服务的日志从头看一遍，找出上面这几行，理解启动到底做了哪些事。

## 3. L1：绕过网关，直连服务

这是最能锻炼理解的一步——**先证明业务本身是对的，再证明网关是对的**。

### 3.1 直连 auth 登录

```powershell
curl.exe -s -X POST http://127.0.0.1:8083/login -H "Content-Type: application/json" -d "{\"account\":\"admin\",\"password\":\"123456\"}"
```

注意路径是 **`/login`**，不是 `/api/auth/login`。

预期：`{"code":0,...,"accessToken":"eyJ...","sessionId":"..."}`

**说明了什么**：auth 服务本身能登录。如果这条失败，就别去看网关，问题在 auth/user/MySQL/Redis。

### 3.2 直连 user 拿资料（必须手动带身份头）

```powershell
# 不带身份头 → 401
curl.exe -s -o NUL -w "无头 status=%{http_code}`n" http://127.0.0.1:8084/profile

# 手动带上 X-User-Id → 200
curl.exe -s -H "X-User-Id: 1" http://127.0.0.1:8084/profile
```

预期：第一条 `401`，第二条返回 `admin / 管理员`。

**说明了什么**：user 完全不看 token，它只信请求头里的 `X-User-Id`。这就是"网关注入身份、下游零鉴权"的设计。**这条验证做完，你就懂了为什么网关是必需的。**

### 3.3 对比：经网关访问同一个接口

```powershell
# 不带 token → 401（被网关拦，根本没到 user）
curl.exe -s -o NUL -w "无token status=%{http_code}`n" http://127.0.0.1:8080/api/user/profile
```

**练习：** 把 3.2 和 3.3 的两个 401 对比一下——一个是 user 返回的（`缺少身份信息`），一个是网关返回的（`未登录或登录已失效`）。**消息不一样，说明拦截点不同。** 这是定位问题时最有用的线索。

## 4. L2：网关路由

### 4.1 登录并提取 token（后面所有实验都要用）

```powershell
$resp = curl.exe -s -X POST http://127.0.0.1:8080/api/auth/login `
  -H "Content-Type: application/json" `
  -d "{\"account\":\"admin\",\"password\":\"123456\",\"deviceType\":\"WEB\"}" | ConvertFrom-Json

$token = $resp.data.accessToken
$sid   = $resp.data.sessionId
"token 前 20 位: " + $token.Substring(0,20)
"sid: $sid"
```

### 4.2 StripPrefix 到底改了什么

| 你请求 | 网关转发到 auth 的路径 |
|---|---|
| `/api/auth/login` | `/login` |

**验证方法**：把 `AuthController` 改成 `@PostMapping("/api/auth/login")`，重启后再直连网关——会 404。改回来。
这个实验能让你彻底记住：**网关剥前缀，Controller 写剥完之后的路径。**

### 4.3 路由是否走负载均衡

```powershell
curl.exe -s "http://127.0.0.1:8848/nacos/v1/ns/instance/list?serviceName=user&namespaceId=public"
```

预期：**只有一条** `port: 8084` 的实例。

> ⚠️ 如果出现 `port: 20882`（Dubbo 端口），说明 Dubbo 应用级注册和服务名撞车了。
> 这是本项目真实踩过的坑，解决方式见主文档「踩坑记录」。

## 5. L3：身份传递与防伪造

### 5.1 网关注入的头是真的吗

```powershell
curl.exe -s -H "Authorization: Bearer $token" http://127.0.0.1:8080/api/user/profile
```
返回 admin 的资料 → 说明网关从 token 解出了 `uid=1` 并注入成功。

### 5.2 客户端伪造身份头，能被拦掉吗（安全实验）

```powershell
# 我不带 token，只伪造一个 X-User-Id，试图冒充
curl.exe -s -o NUL -w "伪造头 status=%{http_code}`n" -H "X-User-Id: 1" http://127.0.0.1:8080/api/user/profile
```
预期：`401`。

**说明了什么**：网关先验签，没 token 一律拒；即使带了 token，`AuthGlobalFilter` 也会**先 `remove` 再 `set`**，所以客户端传的 `X-User-Id: 999` 会被覆盖成真实 uid。

**进阶实验**：登录两个账号（如果注册了第二个），用 A 的 token 请求并伪造 `X-User-Id: B`，看返回的是谁的资料——一定是 A，不会变成 B。

## 6. L4：失效机制（这是整套设计最值钱的部分）

### 6.1 观察 Redis 里的会话

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 keys "auth:*"
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 hgetall "auth:sess:$sid"
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 get "auth:user:1:ver"
```

预期：
- `auth:sess:{sid}` 里有 `uid / deviceType / ip / ua / loginAt / lastSeen`
- `auth:user:1:ver` 是 `0`

### 6.2 实验 A：全端踢人（INCR ver）

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 incr "auth:user:1:ver"
curl.exe -s -H "Authorization: Bearer $token" http://127.0.0.1:8080/api/user/profile
```

预期：`{"code":401,"message":"凭证已失效，请重新登录"}`

**原理**：token 里 `ver=0`，Redis 里变成 `1`，网关比对不相等 → 拒绝。**这就是"封号立即生效"的全部实现。**

**恢复**：重新登录一次，新 token 带 `ver=1`，立刻正常。

### 6.3 实验 B：踢单台设备（DEL sess）

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 del "auth:sess:$sid"
curl.exe -s -o NUL -w "删会话后 status=%{http_code}`n" -H "Authorization: Bearer $token" http://127.0.0.1:8080/api/user/profile
```

预期：**仍然是 200**。

**为什么？** 因为方案 A 里网关只比对 `ver`，不看会话是否存在；token 本身还没过期（30 分钟）。

**这个实验的意义**：让你亲眼看到"没有 `revoked` 黑名单时，踢单台设备有 30 分钟窗口"——这就是文档里「已知限制」的由来，也是后续要补 `auth:revoked:{sid}` 的原因。

### 6.4 对比实验结果

| 实验 | 操作 | 立即生效？ | 原因 |
|---|---|---|---|
| 全端踢人 | `INCR ver` | ✅ 下一次请求就 401 | 网关每请求都比 ver |
| 踢单台 | `DEL sess` | ❌ token 到期前仍可用 | 网关不看 sess |

**做完这两个实验，你就真正理解"为什么要两级机制"了。**

## 7. L5：失败路径

### 7.1 密码错误

```powershell
curl.exe -s -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d "{\"account\":\"admin\",\"password\":\"wrongpass\"}"
```
预期：`{"code":401,"message":"账号或密码错误"}`

同时观察 Redis：

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 get "auth:fail:admin"
```
预期：`1`（再试一次变 2）。

### 7.2 账号不存在

```powershell
curl.exe -s -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d "{\"account\":\"nobody\",\"password\":\"123456\"}"
```
预期：也是 `账号或密码错误`（**故意和密码错一样**，防止探测账号是否存在）。

### 7.3 连续失败 5 次锁定

```powershell
1..5 | ForEach-Object {
  curl.exe -s -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d "{\"account\":\"admin\",\"password\":\"bad\"}" | Out-Null
}
curl.exe -s -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d "{\"account\":\"admin\",\"password\":\"123456\"}"
```
预期：`{"code":429,"message":"失败次数过多，请 15 分钟后再试"}`（**即使密码正确也进不去**）

**解锁**：

```powershell
& "D:\360MoveData\Users\凯宇\Desktop\redis\redis-cli.exe" -p 6379 del "auth:fail:admin"
```

### 7.4 中间件挂掉会怎样（故意搞坏）

| 操作 | 预期现象 | 说明了什么 |
|---|---|---|
| 停 Redis，再登录 | 500 / 503 | auth 强依赖 Redis，fail-close |
| 停 MySQL，再登录 | `系统繁忙`（Dubbo 调 user 查库失败） | 数据层故障会冒泡成 500 |
| 停 user，再登录 | 登录超时/500 | Dubbo 是同步调用，provider 不在就失败 |
| 停 Nacos，已启动的服务 | 仍能跑一阵（本地缓存），但不注册 | 注册中心挂了不等于服务立刻挂 |

**这些实验比看文档有用得多**——你能直接看到"哪个依赖是硬依赖"。

## 8. 三个服务的日志对应关系（定位问题用）

一次登录，三个服务各打什么：

| 服务 | 关键日志 | 位置 |
|---|---|---|
| api-gateway | `token 校验失败`、`鉴权依赖异常`、`凭证已失效` | 网关控制台 |
| auth | `登录成功 userId=1, account=admin, deviceType=WEB, sid=...`、`登录失败 account=..., 累计失败次数=1` | auth 控制台 |
| user | 无登录日志（它只被 Dubbo 调用），查库失败会抛异常 | user 控制台 |

**定位口诀**：

```
登录失败 → 看 auth 日志（有没有进到 passwordEncoder）
带 token 401 → 看网关日志（是验签失败还是 ver 不一致）
系统繁忙 500 → 看 user 日志（是不是数据库连不上）
```

## 11. 五个"故意搞坏"的实验（理解最快的方式）

| 实验 | 怎么做 | 你会看到 |
|---|---|---|
| 让网关和 auth 密钥不一致 | 改网关 `gateway.auth.secret` 加一个字符，重启 | 所有请求 401 `登录已失效` → 明白验签是共享密钥 |
| 让 JWT 过期 | 把 `jwt.expire-seconds` 改成 10，重启登录，等 10 秒 | 401 → 明白 exp 的作用 |
| 让 Controller 路径带前缀 | `@PostMapping("/api/auth/login")` | 经网关 404 → 明白 StripPrefix |
| 让 Dubbo 恢复应用级注册 | 去掉 `register-mode: interface` | 网关开始随机 500 → 明白服务名撞车的可怕 |
| 让 user 不信任头、改看 token | （不推荐改，思考即可） | 每个服务都要重复写鉴权 → 明白为什么要网关统一做 |

## 12. 一句话总结

> **L0 看端口，L1 直连服务，L2 过网关，L3 看头，L4 删数据，L5 断依赖。**
> 每层只改一个变量，每步只问一句"如果这里错了，会看到什么现象"。这样验证一遍，比读十遍文档都牢。

## 附：验证脚本（可选）

如果不想每次敲命令，可以在项目根目录建 `verify.ps1`，内容如下：

```powershell
$ErrorActionPreference = 'Stop'
function Step($name, $actual, $expect) {
  $ok = $actual -like "*$expect*"
  Write-Host ("{0} {1}" -f $(if($ok){'[PASS]'}else{'[FAIL]'}), $name) -ForegroundColor $(if($ok){'Green'}else{'Red'})
}

# 1. 网关无 token
$r = curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:8080/api/user/profile
Step "网关无 token 应 401" $r "401"

# 2. 登录
$body = '{"account":"admin","password":"123456","deviceType":"WEB"}'
$resp = curl.exe -s -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d $body | ConvertFrom-Json
Step "登录 code=0" $resp.code "0"

# 3. 带 token
$t = $resp.data.accessToken
$p = curl.exe -s -H "Authorization: Bearer $t" http://127.0.0.1:8080/api/user/profile | ConvertFrom-Json
Step "带 token 拉资料" $p.code "0"
Step "昵称正确" $p.data.account "admin"
```
