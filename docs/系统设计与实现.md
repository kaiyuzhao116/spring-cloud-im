> 更新时间：2026-10-22

## 1. 项目概述

目标是构建一个支撑 IM（即时通讯）的微服务底座：HTTP 走网关，实时消息将来走 Netty 长连接，服务间调用走 Dubbo，异步事件走 RocketMQ（未接入）。

当前已实现的两个闭环：

```
① 登录（HTTP）
浏览器(Vue) → api-gateway(验签/注入身份) → auth(签发 token) → Dubbo → user(查库) → MySQL

② 发消息（WebSocket）
客户端 ──WS──▶ ws-gateway(Netty 验签/收帧)
                  │ Dubbo
                  ▼
                 im ──▶ MySQL（消息 + 双方会话卡片，Redis 分配 seq）
                  │ 事务提交后发事件
                  ▼
             RabbitMQ（im.events / message.created）
                  │ 广播给所有 ws 实例（各自匿名队列）
                  ▼
             ws-gateway 查本机连接 → 推给接收方
```

## 4. 登录链路

### 4.1 时序

```
① 浏览器 POST /api/auth/login {account, password, deviceType}
② api-gateway:8080
     - 路径命中白名单 → 跳过验签
     - 路由 /api/auth/** → lb://auth，StripPrefix=2 后转发 /login
③ auth:8083
     - @Valid 参数校验
     - 失败次数检查 auth:fail:{account}（≥5 直接 429）
     - Dubbo 调 user.getByAccount()
     - BCrypt 校验密码（失败则 INCR 失败计数并返回统一错误）
     - 签发 JWT（精简版：sub / iat / exp）
④ 返回 {userId, nickname, accessToken, expiresIn, deviceType}
⑤ 后续请求 Authorization: Bearer <token>
     - 网关验签 → 注入 X-User-Id → 下游从 UserContext 取身份
```

> **2026-10-22 变更**：token 精简为 `sub / iat / exp` 三个字段，会话写入与版本号校验已从代码中移除。
> 踢人、单端登出、多端区分等能力暂时不可用，恢复方式见 5.3 与第 12 章。

### 4.2 路径对应关系

| 外部（经网关） | 网关处理后 | auth 服务内 |
|---|---|---|
| `/api/auth/login` | `StripPrefix=2` | `/login` |
| `/api/auth/logout` | `StripPrefix=2` | `/logout` |
| `/api/user/profile` | `StripPrefix=2` | `/profile` |

> 网关 `StripPrefix=2`，所以 Controller 里**不要**再写 `/api/auth` 前缀。

## 5. 鉴权设计

### 5.1 职责划分

| 组件 | 负责 | 不负责 |
|---|---|---|
| `api-gateway` | 白名单、JWT 验签、注入 `X-User-Id`、剥离伪造头 | 查库、查会话、签发 token、访问 Redis（精简版后不再访问） |
| `auth` | 密码校验、token 签发、失败计数 | 用户资料维护、会话管理（精简版已移除） |
| `user` | 用户数据，暴露 Dubbo 接口与资料 REST | 密码校验、鉴权 |
| 业务服务 | 从 `UserContext` 取身份，**不解析 token** | — |

### 5.2 JWT 内容（精简版）

```json
{ "sub": "1", "iat": 1792651070, "exp": 1792652870 }
```

| 字段 | 含义 | 网关怎么用 |
|---|---|---|
| `sub` | 用户 ID | 解出后注入 `X-User-Id` |
| `iat` | 签发时间 | 仅用于排查（"什么时候登的"） |
| `exp` | 过期时间 | 验签时自动校验，过期即 401 |

- 三个字段，token 约 180 字符（原四字段版本 228 字符）
- 签名：jjwt 按密钥长度自动选择，当前 57 字节密钥 → **HS384**
- payload 是 base64url **明文可读**，因此不放密码、手机号、权限明细
- 生产建议改 RS256（auth 持私钥，网关只放公钥）

### 5.3 失效机制（当前：无服务端失效）

精简版移除了 `sid` 与 `ver`，因此：

| 能力 | 现状 | 原因 |
|---|---|---|
| 主动踢人（单端/全端） | ❌ 只能等 token 过期（≤30 分钟） | token 里没有可对账的标识 |
| 退出登录 | ❌ 仅客户端删除 token，服务端无感知 | `logout` 是空实现 |
| 多端区分 | ❌ 无 `sid` / `dev` | 网关不再注入 `X-Session-Id` / `X-Device-Type` |
| 封号（DB `status=0`） | ⚠️ 只影响新登录，已发 token 仍有效到过期 | 网关不查库 |

**恢复能力的三步**（需要时按顺序加）：

1. `JwtManager.sign` 增加 `.claim("sid", sid).claim("ver", ver)`
2. `AuthService` 恢复写会话（`HSET auth:sess:{sid}` + `SETNX auth:user:{uid}:ver 0`），并把两个值传给 `sign`
3. `AuthGlobalFilter` 恢复读取 claims 并比对 Redis 的 `ver`

> 完整设计（五个 key、两级失效、`revoked` 黑名单）见 git 历史中的旧设计稿，或按第 12 章逐步补。

### 5.4 网关校验成本

每请求 = **1 次本地验签（约 0.1ms）**，不访问 Redis、不调用 auth。
这是精简版最大的收益：网关完全无状态，扩缩容无成本。

代价是"无法即时撤销" —— 需要即时踢人时必须在网关加回 Redis 版本号比对。

## 6. 数据模型

### 6.1 MySQL

```sql
-- db/schema.sql
CREATE TABLE sys_user (
  id            BIGINT UNSIGNED AUTO_INCREMENT,
  account       VARCHAR(64)  NOT NULL,          -- 登录账号，唯一
  password_hash VARCHAR(100) NOT NULL,          -- BCrypt cost 10
  nickname      VARCHAR(64)  NOT NULL DEFAULT '',
  avatar        VARCHAR(255) DEFAULT NULL,
  status        TINYINT      NOT NULL DEFAULT 1, -- 1 正常 0 禁用
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id), UNIQUE KEY uk_account (account)
);
```

测试数据：`admin / 123456`（BCrypt：`$2a$10$oAhOz9YQMsvL...hxLo6`）

连接：`jdbc:mysql://127.0.0.1:3306/spring_cloud`，root/123456，物理文件
`C:\ProgramData\MySQL\MySQL Server 8.0\Data\spring_cloud\sys_user.ibd`

### 6.2 Redis

| key | 类型 | TTL | 状态 | 说明 |
|---|---|---|---|---|
| `auth:fail:{account}` | STRING 整数 | 15 分钟 | ✅ **在用** | 登录失败计数（防撞库） |
| `auth:sess:{sid}` | HASH：`uid/deviceType/ip/ua/loginAt/lastSeen` | 7 天 | ⏸ 停用 | 精简版后代码不再写入；历史遗留会自然过期 |
| `auth:user:{uid}:ver` | STRING 整数 | 无 | ⏸ 停用 | 精简版后代码不再读写；恢复"即时踢人"时需要它 |

> 停用的两个 key 对应的能力与恢复步骤见 5.3；Redis 里已有的旧 key 不影响运行，可以手动清掉：
> `redis-cli --scan --pattern "auth:sess:*" | xargs redis-cli del`（或忽略，等 TTL 过期）。

> 尚未实现：`auth:user:{uid}:sessions`（设备名册）、`auth:rt:{sid}`（refreshToken）、`auth:revoked:{sid}`（临时黑名单）。

## 8. 关键配置

### 8.1 JWT（auth 与网关必须一致）

```yaml
# auth
jwt:
  secret: spring-cloud-im-demo-jwt-secret-key-please-change-in-prod
  expire-seconds: 1800
  session-ttl-seconds: 604800
  max-fail-count: 5
  fail-window-seconds: 900

# api-gateway
gateway:
  auth:
    secret: spring-cloud-im-demo-jwt-secret-key-please-change-in-prod
```

### 8.2 Dubbo（避免与服务名冲突，必须这么配）

```yaml
# 提供方
dubbo:
  application:
    name: user
    register-mode: interface      # 只做接口级注册
# 消费方（auth / ws-gateway）
dubbo:
  application:
    service-discovery:
      migration: FORCE_INTERFACE
```

### 8.3 数据源与 Redis

```yaml
spring:
  datasource:            # 仅 user 模块
    url: jdbc:mysql://127.0.0.1:3306/spring_cloud?useSSL=false&characterEncoding=utf8&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true
    username: root
    password: "123456"
  data:
    redis:               # auth / api-gateway
      host: 127.0.0.1
      port: 6379
```

### 8.4 本地无 Nacos 模式

各服务已内置 `local` profile：`--spring.profiles.active=local` 时关闭 Nacos 并把 `dubbo.registry.address` 设为 `N/A`，可脱离注册中心启动 Web 部分。

## 10. 已验证用例

| 用例 | 结果 |
|---|---|
| 网关登录 `admin/123456` | `code=0`，返回 `userId/nickname/accessToken/expiresIn` |

## 11. 踩坑记录

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | 网关报 `invalid version format: UNSUPPORTED` | Dubbo 3.2 应用级注册把 `user` 注册到 20882，与 Spring Cloud 的 `user:8084` 撞名，`lb://user` 轮询打到 Dubbo 端口 | 提供方 `register-mode: interface`，消费方 `migration: FORCE_INTERFACE` |
| 2 | 下游一直报"缺少身份信息" | `default-filters: RemoveRequestHeader` 在 GlobalFilter 之后执行，删掉了刚注入的头 | 去掉 default-filters，剥离逻辑放在 `AuthGlobalFilter` 内部（先 remove 再 set） |
| 3 | 编译报 `NoSuchFieldError: JCTree$JCImport.qualid` | Boot 3.0.2 锁 Lombok 1.18.24，不支持 JDK 21 | 父 pom `dependencyManagement` 显式指定 1.18.30（BOM 内属性无法被外部属性覆盖） |
| 4 | common 模块编译找不到 `HandlerInterceptor` / `HttpServletRequest` | 该模块只依赖了 `spring-boot-starter` | 增加 `spring-webmvc`、`jakarta.servlet-api`，均为 `optional`，不传递给 WebFlux 网关 |
| 5 | 双击 `启动Redis.cmd` 报 `'动日志...' 不是内部或外部命令`，并反复刷屏 | 脚本存成 UTF-8 + LF，且含 `if (...)` 多行括号块，cmd 按代码页逐字节解析时把中文行切断 | `.cmd` 统一用 **GBK（代码页 936）+ CRLF**，并避免多行 `if (...)`，改用 `goto` 跳转 |

## 13. 已知限制（当前版本）

| 限制 | 影响 | 是否需要尽快处理 |
|---|---|---|
| **无法即时踢人**（token 无 sid/ver） | 封号后已发出的 token 仍可用到过期（≤30 分钟） | 视业务，有管理需求就要补 |
| **退出登录是客户端行为** | 服务端无感知，旧 token 仍有效 | 同上 |
| **无 sid / dev** | 后台看不到设备、无法单端下线、下游拿不到设备类型 | 同上 |
| 无名册 | 后台无法列出"某用户有哪些设备" | 做后台时 |
| 无 refreshToken | 30 分钟后必须重新输账号密码 | 上生产前 |
| HS384 共享密钥 | 网关需持签发密钥，建议换 RS256 | 上线前 |
| 登录无 IP 限流 | 只按账号计数，密码喷洒防不住 | 有攻击迹象时 |
| 网关不查库 | 封号（`status=0`）只影响新登录 | 与第一条一起处理 |
| ~~无历史消息接口~~ | 已解决：`GET /api/im/messages` | ✅ |
| ~~无离线补偿~~ | 已解决：重连带 `afterSeq` 补缺口 | ✅ |
| **无投递回执** | "发送成功"只代表服务端已持久化，不代表对方收到 | 需要时再加 |
| **无在线状态** | 界面上"已连接"其实是自己的连接状态，不是对方的 | 可用 `OnlineRegistry.list` 做接口 |
| **单端登录不彻底** | 只踢"更早建立"的连接；两台同时登录可能都活下来 | 可加设备维度 |
| **无频率限制** | 一个合法连接可以狂发小消息刷爆 im | 建议尽快补（见 19.4） |
| MQ 推送为单机验证 | 目前只跑一台 ws-gateway，广播价值未体现 | 扩容时自然生效 |

## 14. IM 消息链路（已实现）

### 14.1 一次发送的完整时序

```
A 客户端           ws-gateway               im                    RabbitMQ           B 客户端
   │                   │                    │                       │                  │
   │ ①MSG 帧           │                    │                       │                  │
   ├──────────────────▶│                    │                       │                  │
   │                   │ ②取连接身份 userId │                       │                  │
   │                   │   丢业务线程池      │                       │                  │
   │                   │ ③Dubbo send        │                       │                  │
   │                   ├───────────────────▶│                       │                  │
   │                   │                    │ ④幂等 → seq → 事务     │                  │
   │                   │                    │   写 3 条 SQL          │                  │
   │                   │                    │ ⑤提交后发事件          │                  │
   │                   │                    ├──────────────────────▶│                  │
   │ ⑥ACK(cid,seq)     │                    │                       │ ⑦广播给各实例     │
   │◀──────────────────┤◀───────────────────┤                       ├─────────────────▶│
   │                   │                    │                       │                  │
   │                   │◀───────────────────────────────────────────┤ ⑧推给本机连接     │
   │                   ├──────────────────────────────────────────────────────────────▶│
```

### 14.2 ACK 与推送是两条独立的线

| | ACK | 消息推送 |
|---|---|---|
| 触发 | `imClient.send()` 返回后 | MQ 事件被消费后 |
| 目标 | **发送方**（手里有 `ctx`，直写） | **接收方**（不知道连在哪 → 必须广播） |
| 是否依赖对方在线 | 否 | 是（不在线就命中 0 条连接） |
| 失败影响 | 不影响消息存在 | 不影响发送方成功 |

**结论：ACK 只代表"服务端已持久化"，不代表"对方已收到"。**

### 14.3 各环节代码位置

| 环节 | 文件 |
|---|---|
| 收帧 / 身份 / ACK | `ws-gateway/.../handler/BusinessHandler.java` |
| 握手验签 / 写 userId | `ws-gateway/.../handler/AuthHandshakeHandler.java` |
| Dubbo 客户端 | `ws-gateway/.../support/ImClient.java` |
| 落库业务 | `im/.../service/MessageService.java` |
| seq 生成 | `im/.../service/SeqGenerator.java` |
| 事件发布 | `im/.../mq/MessageEventPublisher.java` |
| MQ 消费推送 | `ws-gateway/.../mq/MessagePushListener.java` |
| 连接表 / 推送 | `ws-gateway/.../session/ChannelManager.java` |

### 14.4 失败矩阵

| 失败点 | 发送方看到 | 接收方看到 | 消息是否丢失 |
|---|---|---|---|
| 校验不通过 | 无 ACK（帧被丢弃） | 无 | 未产生 |
| im 抛异常 / 超时 | ACK `seq=0` → "发送失败" | 无 | 未产生 |
| MQ 发送失败 | ACK 正常 | 收不到实时推送（可拉取） | 不丢 |
| MQ 卡住 | ACK 延迟（publish 同步） | 延迟收到 | 不丢 |
| 接收方离线 | ACK 正常 | 无 | 不丢（在库里） |

## 15. WebSocket 接入层（ws-gateway）

### 15.1 职责边界

| 负责 | 不负责 |
|---|---|
| 连接管理、握手验签、协议升级 | 落库、生成 seq |
| 帧编解码、心跳、空闲踢人 | 业务规则（谁能发给谁） |
| 把帧转成 Dubbo 调用 | 知道用户在哪台实例（靠 MQ 广播规避） |
| 消费 MQ 并写回连接 | 消息存储与查询 |

### 15.2 Pipeline（顺序不可调）

```
HttpServerCodec → HttpObjectAggregator → AuthHandshakeHandler
   → WebSocketServerProtocolHandler → IdleStateHandler
   → BusinessHandler → ConnectionHandler
```

关键点：

- `HttpObjectAggregator` 必须在验签之前（否则拿不到完整请求）
- `AuthHandshakeHandler` 必须在升级之前（否则无法回 401）
- `WebSocketServerProtocolHandler` 需 `checkStartsWith(true)`，否则 `/ws?token=xxx` 匹配不上
- `ConnectionHandler` 靠 `HandshakeComplete` 事件登记 connId

### 15.3 帧协议（最小版）

| type | 方向 | 字段 |
|---|---|---|
| `MSG` | 双向 | 上行：`cid` `to` `content`；下行：`from` `seq` `content` |
| `ACK` | 下行 | `cid` `seq`（`seq=0` 表示失败） |
| `PING` / `PONG` | 双向 | 无 |

铁律：`from` / `seq` 只能服务端生成；`cid` 只能客户端生成。

### 15.4 线程模型

```
EventLoop（默认 CPU×2）
  ├─ 解码、校验、心跳（轻量）
  └─ MSG → bizExecutor（8 线程，有界队列 5000，CallerRunsPolicy）
                └─ Dubbo 阻塞调用 → 回调 writeAndFlush
```

- **EventLoop 里绝不做阻塞调用**，否则拖死该线程上的所有连接
- 业务池用有界队列 + `CallerRunsPolicy`：满了由 IO 线程自己跑，形成背压，避免 OOM

### 15.5 心跳与断连

| 项 | 值 |
|---|---|
| 客户端心跳 | 30 秒一次 `PING` |
| 服务端空闲检测 | `IdleStateHandler(0,0,60)` → 触发后 `close` |
| 关闭码约定 | 4001 被踢（不重连）、4002 token 过期（刷新后重连）、4003 服务重启 |

### 15.6 多实例与 MQ 广播

- 每个 `ws-gateway` 实例声明**匿名、独占、自动删除**的队列，绑定同一个 `im.events` 交换机
- 共用队列会变成竞争消费（只有一台收到），**必须每实例一个**
- 消费端按 `toUid` 查本机连接表，命中就写帧，未命中直接丢弃

### 15.7 尚未实现

| 项 | 状态 |
|---|---|
| ~~Redis 在线表 `ws:online:{uid}`~~ | ✅ 已实现（HASH + TTL 120s + PING 续期，见第 19 章） |
| ~~单端登录踢人（4001）~~ | ✅ 已实现（MQ 广播 kick，见第 19 章） |
| ~~断线重连按 `lastSeq` 补拉~~ | ✅ 已实现（`afterSeq`，见第 18 章） |
| Token 到期主动 `close(4002)` | ⬜ 未做 |
| 每连接频率限制 | ⬜ 未做 |
| 管理后台强制下线（需 `sid/ver`） | ⬜ 未做 |

## 16. IM 数据模型与 seq

### 16.1 两张表

| 表 | 一行代表 | 索引要点 |
|---|---|---|
| `im_message` | 一条消息 | `uk_conv_seq(conversation_id,seq)` 保序、`uk_client(from_uid,client_msg_id)` 幂等 |
| `im_conversation_member` | 某人在某会话的视图 | `uk_conv_uid` 一人一会话一行、`idx_uid_time(uid,last_msg_at)` 会话列表 |

单聊一个会话 2 行（双方各一行），群聊 N 行。

### 16.2 发一条消息写三条记录（同一事务）

```sql
INSERT im_message (...);
INSERT im_conversation_member (...) ON DUPLICATE KEY UPDATE last_seq=VALUES(last_seq),
    last_read_seq=VALUES(last_read_seq), ...;   -- 发送方：自己发的算已读
INSERT im_conversation_member (...) ON DUPLICATE KEY UPDATE last_seq=VALUES(last_seq), ...;
                                                -- 接收方：只推 last_seq，未读 +1
```

### 16.3 seq 生成

```java
if (!exists(key)) {                       // Redis 被清空/重启
    max = SELECT MAX(seq) FROM im_message WHERE conversation_id=?;
    SETNX key max;                        // 从库里恢复，避免从 1 重来撞唯一键
}
seq = INCR im:seq:{conversationId};       // 原子，并发不撞号
```

要点：seq 是**会话内**连续编号，`id` 是全局自增；事务回滚时 seq 不回退（会有空洞，可接受）。

### 16.4 未读 = 减法

```sql
last_seq - last_read_seq AS unread
```

不存 `unread_count`，避免"多发/漏加"导致的永久错位。

## 18. 读路径：历史 / 会话列表 / 未读 / 已读

### 18.1 三个接口

| 接口 | 用途 | 关键参数 |
|---|---|---|
| `GET /api/im/messages` | 拉消息（翻历史或补缺口） | `conv` + `beforeSeq` 或 `afterSeq` + `limit` |
| `GET /api/im/conversations` | 会话列表 + 未读 | `limit` |
| `POST /api/im/read` | 上报已读位置 | `{"conv":"s_1_2","seq":43}` |

三个接口都从 `X-User-Id` 取身份（网关注入），并校验会话归属。

### 18.2 一个接口两种语义

| 参数 | 方向 | SQL | 用途 |
|---|---|---|---|
| `beforeSeq`（默认 0 = 最新） | 往前翻 | `seq < ? ORDER BY seq DESC LIMIT ?` | 打开会话 / 上滑加载 |
| `afterSeq` | 往后补 | `seq > ? ORDER BY seq ASC LIMIT ?` | 断线重连补缺口 |

**都返回升序**：前端拿到就能直接渲染，不用自己反转。

**`hasMore` 的算法**：多取一条（`limit + 1`），多出来了说明还有，然后截掉。

### 18.3 前端分页与合并

| 策略 | 值 | 原因 |
|---|---|---|
| 首次加载 | 30 条 | 首屏够看，请求小 |
| 每次上滑/点击 | 20 条 | 增量友好 |
| 内存上限 | 300 条 | 防止 DOM 无限增长 |
| 去重 | 按 `seq` | 历史 / 实时 / 翻页三者可能重叠 |
| 加载更多后 | `scrollTop += 高度差` | 保证视口不跳 |

**顺序很重要**：先 `loadHistory()` 再 `connect()`，否则实时消息会被历史覆盖。

### 18.4 未读与已读

**未读不存字段**，永远是减法：

```sql
unread = last_seq - last_read_seq
```

**已读上报只增不减**：

```sql
UPDATE im_conversation_member
SET last_read_seq = GREATEST(last_read_seq, ?)
WHERE conversation_id = ? AND uid = ?
```

**前端三个上报时机**：打开会话、正在看的会话收到新消息、重连补齐之后。**同一个 seq 只上报一次**（本地记 `readSent`）。

### 18.5 越权保护

```java
if (!ConversationId.contains(conversationId, uid)) {
    throw new BizException(403, "无权查看该会话");
}
```

`ConversationId.contains("s_1_2", 3)` → false。**所有涉及会话的接口都必须过这一关**，否则改个 `conv` 参数就能读别人的聊天记录。

### 18.6 索引是否用上

| 查询 | 命中索引 |
|---|---|
| `WHERE conversation_id = ? AND seq < ?` | `uk_conv_seq(conversation_id, seq)` range |
| `WHERE conversation_id = ? AND seq > ?` | 同上 |
| `WHERE uid = ? ORDER BY last_msg_at DESC` | `idx_uid_time(uid, last_msg_at DESC)` |

**会话列表不回消息表**——所有展示字段（预览、时间、seq）都在 `im_conversation_member` 里，一张表就够。

## 19. 单端登录与在线表

### 19.1 要解决什么

```
同一个人在手机和电脑上同时登录
   ↓ 消息推两份？未读算谁的？被盗用怎么发现？
   ↓
单端：一个账号同时只允许一条连接，新登录踢掉旧的
```

### 19.2 三段式机制

```
① 新连接握手成功
     → 写入在线表 ws:online:{uid}
     → 广播 KickEvent{uid, excludeConnId=自己, newConnTime}

② 所有实例（含本机）消费该事件
     → 各自查本机连接表
     → 踢掉"该用户 + 不是 excludeConnId + 比 newConnTime 更早"的连接

③ 踢的方式
     → 标记 CLOSE_REASON = KICKED
     → 发 CloseWebSocketFrame(4001) → addListener(CLOSE)
     → 客户端收到 4001 → 不重连
```

**为什么必须广播而不是本机踢**：多实例时旧连接可能在**另一台机器**上，本机表里根本没有。

**为什么必须带 4001**：直接 `close()` 客户端只看到 1006（异常），会当成网络问题自动重连，随后又把新连接踢掉，形成互踢循环。

### 19.3 Redis 在线表

```
key   : ws:online:{uid}          HASH
field : connId
value : 实例地址 127.0.0.1:8089
TTL   : 120 秒
```

| 动作 | 时机 | 命令 |
|---|---|---|
| 登记 | 握手成功 | `HSET` + `EXPIRE` |
| **续期** | **收到客户端 PING（25 秒一次）** | `EXPIRE` |
| 移除 | `channelInactive` | `HDEL connId`（**不是 DEL key**） |

**三条铁律**：
1. 用 HASH 不用 String —— 一个用户可能多条连接，String 会互相覆盖
2. 删除只 `HDEL` 单个 field —— `DEL` 会误删同账号其它连接
3. 必须续期 —— 否则 120 秒后活着的连接被误判离线

### 19.4 竞态与边界

| 边界 | 处理 |
|---|---|
| 遍历时集合被修改（踢人 → 注销 → 删元素） | 先复制成 `List` 再遍历 |
| 踢到自己 | 先踢后登记 + `excludeConnId` 双重防护 |
| **事件乱序**（1 秒内重连两次） | 只踢比 `newConnTime` 更早的连接，旧事件自动失效 |
| 踢一条已半死的连接 | `isActive()` 判断，不活跃就直接 `close()` 触发清理 |
| 旧连接正在处理消息 | 落库成功但 ACK 写不进去（`isActive=false`）→ 用户重连后能从历史里看到 |
| 两台设备同时握手 | 都带着"自己是最新"的时间戳，可能都存活（**已知局限**） |

### 19.5 关闭码约定

| 码 | 含义 | 客户端行为 |
|---|---|---|
| 1006 | 异常断开（没有 Close 帧） | 自动重连 |
| 1009 | 单帧超 4KB | 不重连，提示"消息过大" |
| **4001** | **同账号在别处登录** | **不重连**，提示"已在其他设备登录" |
| 4002 | token 过期（未实现） | 不重连，提示重新登录 |
| 4003 | 服务重启（未实现） | 退避重连 |

### 19.6 还没做

| 缺口 | 说明 |
|---|---|
| 频率限制 | 单端只解决"几条连接"，没解决"发多快" |
| 在线状态接口 | `OnlineRegistry.list()` 已就绪，尚未暴露 HTTP |
| 设备维度单端 | 需要 token 里带 `dev`，才能做"同类型互踢、不同类型共存" |
| 强制下线 | 需要 `sid/ver`，属于 P3 |
