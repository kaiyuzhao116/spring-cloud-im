## 1. 项目概述

目标是构建一个支撑 IM（即时通讯）的微服务底座：HTTP 走网关，实时消息将来走 Netty 长连接，服务间调用走 Dubbo，异步事件走 RocketMQ（未接入）。

当前已实现的两个闭环：

```
① 登录（HTTP）
浏览器(Vue) → api-gateway(验签/注入身份) → auth(签发 token) → Dubbo → user(查库) → MySQL

② 发消息（WebSocket）
客户端 ──WS──▶ ws-gateway(Netty 验签/收帧)
                  │ Dubbo
                  ▼
                 im ──▶ MySQL（消息 + 双方会话卡片，Redis 分配 seq）
                  │ 事务提交后发事件
                  ▼
             RabbitMQ（im.events / message.created）
                  │ 广播给所有 ws 实例（各自匿名队列）
                  ▼
             ws-gateway 查本机连接 → 推给接收方
```

## 4. 登录链路

### 4.1 时序

```
① 浏览器 POST /api/auth/login {account, password, deviceType}
② api-gateway:8080
     - 路径命中白名单 → 跳过验签
     - 路由 /api/auth/** → lb://auth，StripPrefix=2 后转发 /login
③ auth:8083
     - @Valid 参数校验
     - 失败次数检查 auth:fail:{account}（≥5 直接 429）
     - Dubbo 调 user.getByAccount()
     - BCrypt 校验密码（失败则 INCR 失败计数并返回统一错误）
     - 签发 JWT（精简版：sub / iat / exp）
④ 返回 {userId, nickname, accessToken, expiresIn, deviceType}
⑤ 后续请求 Authorization: Bearer <token>
     - 网关验签 → 注入 X-User-Id → 下游从 UserContext 取身份
```

> **2026-10-22 变更**：token 精简为 `sub / iat / exp` 三个字段，会话写入与版本号校验已从代码中移除。
> 踢人、单端登出、多端区分等能力暂时不可用，恢复方式见 5.3 与第 12 章。

### 4.2 路径对应关系

| 外部（经网关） | 网关处理后 | auth 服务内 |
|---|---|---|
| `/api/auth/login` | `StripPrefix=2` | `/login` |
| `/api/auth/logout` | `StripPrefix=2` | `/logout` |
| `/api/user/profile` | `StripPrefix=2` | `/profile` |

> 网关 `StripPrefix=2`，所以 Controller 里**不要**再写 `/api/auth` 前缀。

## 5. 鉴权设计

### 5.1 职责划分

| 组件 | 负责 | 不负责 |
|---|---|---|
| `api-gateway` | 白名单、JWT 验签、注入 `X-User-Id`、剥离伪造头 | 查库、查会话、签发 token、访问 Redis（精简版后不再访问） |
| `auth` | 密码校验、token 签发、失败计数 | 用户资料维护、会话管理（精简版已移除） |
| `user` | 用户数据，暴露 Dubbo 接口与资料 REST | 密码校验、鉴权 |
| 业务服务 | 从 `UserContext` 取身份，**不解析 token** | — |

### 5.2 JWT 内容（精简版）

```json
{ "sub": "1", "iat": 1792651070, "exp": 1792652870 }
```

| 字段 | 含义 | 网关怎么用 |
|---|---|---|
| `sub` | 用户 ID | 解出后注入 `X-User-Id` |
| `iat` | 签发时间 | 仅用于排查（"什么时候登的"） |
| `exp` | 过期时间 | 验签时自动校验，过期即 401 |

- 三个字段，token 约 180 字符（原四字段版本 228 字符）
- 签名：jjwt 按密钥长度自动选择，当前 57 字节密钥 → **HS384**
- payload 是 base64url **明文可读**，因此不放密码、手机号、权限明细
- 生产建议改 RS256（auth 持私钥，网关只放公钥）

### 5.3 失效机制（当前：按"签发时间"作废）

精简版移除了 `sid` 与 `ver`，改用更简单的**时间线**方案：

```
key   : auth:kicked:{uid}
value : 踢出时刻（毫秒）
规则  : token 的 iat < 该值 → 403/401 拒绝
TTL   : 30 分钟（= token 有效期，记录自动消失）
```

| 能力 | 现状 | 说明 |
|---|---|---|
| **管理员强制下线** | ✅ 断连接 + token 作废 | 见第 24 章；刷新也进不来，必须重新登录 |
| 单端登录踢旧连接 | ✅ 只断连接，**不作废 token** | 换浏览器登录后旧连接刷新仍可连（符合预期） |
| 退出登录 | ❌ 仅客户端删除 token | `logout` 是空实现 |
| 多端区分 | ❌ 无 `sid` / `dev` | 需要 `dev` 才能做"同类型互踢" |
| 封号（DB `status=0`） | ⚠️ 只影响新登录 | 网关不查库；需要彻底封禁时配合 `auth:kicked:{uid}` |

**为什么用"签发时间"而不是 `ver`/`sid`**：

| 方案 | 改动面 |
|---|---|
| sid / ver | 要改 JWT 结构 + 签发逻辑 + 网关 + 会话表 |
| **iat + 作废线** | **JWT 不动**，只加一个 Redis key；语义也准确（"此刻之前的凭证作废"） |

**局限**：同一秒内签发的新 token 可能被误判（踩到时间精度）。实际影响极小，
真要杜绝就给 token 加 `jti` + 白名单。

### 5.4 网关校验成本

每请求 = **1 次本地验签（约 0.1ms）+ 1 次 Redis GET（约 0.2ms）**。

- Redis 异常时**放行**（可用性优先），不会因为 Redis 抖动把所有人踢下线
- 想进一步降耗可加 3~5 秒本地缓存（代价：踢人生效最多延迟几秒）
- 网关仍**不查库、不调用 auth**，扩缩容无额外成本

代价是"无法即时撤销" —— 需要即时踢人时必须在网关加回 Redis 版本号比对。

### 5.5 滑动续期（活跃用户不会被登出）

**问题**：token 只有 30 分钟，用户聊着天按一下刷新就被踢回登录页。

**解法**：趁票还没过期，用旧票换新票。

```
前端：请求前检查，剩余 < 5 分钟 → POST /api/auth/renew（带旧票）
   ↓ auth 四道校验
   ↓ 通过 → 签一张新票返回
   ↓ 前端覆盖本地 token
```

**四道校验（缺一不可）**：

| # | 校验 | 防的问题 |
|---|---|---|
| 1 | 签名正确 | 伪造一张票来换 |
| 2 | 过期不超过 **10 分钟宽限** | 拿几个月前的旧票换新票 |
| 3 | **未被管理员作废**（比对 `auth:kicked:{uid}` 与 `iat`） | 被踢的人借续签复活 |
| 4 | 账号未被禁用 | 封号用户续出新票 |

**为什么签发权不放网关**：

| 方案 | 后果 |
|---|---|
| 网关签票 | 网关被攻破 = 能伪造任意用户 token（门卫自己印证） |
| **auth 签票**（现在） | 网关只验票，职责纯粹；代价是每 20 分钟多一次 2ms 请求 |

**为什么 `/api/auth/renew` 在网关白名单里**：

```
旧票可能"刚刚过期" → 走网关会直接 401 → 永远续不上
所以放行，由 auth 自己用宽限期判断（但它仍然完整校验签名/作废/账号状态）
```

**前端为什么有两层**：

| 层 | 时机 | 解决 |
|---|---|---|
| 第 1 层 | 请求前，剩余 < 5 分钟 | 正常活跃用户（覆盖 95%） |
| 第 2 层 | 已被 401 拦下 | **潜水用户**（挂了半天才回来）→ 续一次再重试原请求 |

**并发保护**：三个请求同时发现要续签 → 单飞锁保证只发一次，其余等同一张新票。

> 将来 access token 想缩到 5 分钟、或换 RS256（网关只持公钥、无法自签），才需要升级为 refreshToken 方案。

## 6. 数据模型

### 6.1 MySQL

```sql
-- db/schema.sql
CREATE TABLE sys_user (
  id            BIGINT UNSIGNED AUTO_INCREMENT,
  account       VARCHAR(64)  NOT NULL,          -- 登录账号，唯一
  password_hash VARCHAR(100) NOT NULL,          -- BCrypt cost 10
  nickname      VARCHAR(64)  NOT NULL DEFAULT '',
  role          VARCHAR(16)  NOT NULL DEFAULT 'user',  -- user/admin，后台接口按此校验
  avatar        VARCHAR(255) DEFAULT NULL,
  status        TINYINT      NOT NULL DEFAULT 1, -- 1 正常 0 禁用
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id), UNIQUE KEY uk_account (account)
);
```

### 6.1.1 IM 与社交表

```sql
-- db/im_schema.sql
im_message             -- 消息本体，uk_conv_seq 保序、uk_client 幂等；
                       -- recalled=1 表示已撤回（content 被清空，行保留以维持 seq 连续）
im_conversation_member -- 每人每会话一行（预览/seq/已读），idx_uid_time 支撑会话列表
im_friend              -- 好友关系，**双向各一行**，uk_uid_friend 让"查我的好友"走索引
im_friend_request      -- 好友申请，uk_from_to 保证同一对用户只有一条记录
```

| 表 | 关键索引 | 支撑的查询 |
|---|---|---|
| `im_friend` | `uk_uid_friend(uid, friend_uid)` | 是否好友、好友列表 |
| `im_friend_request` | `uk_from_to(from_uid, to_uid)`、`idx_to_status(to_uid, status)` | 防重复申请、拉收到的待处理申请 |

**为什么好友关系存两行**：单行 `(min,max)` 查询要 `WHERE a=? OR b=?`，用不上索引；
两行方案"查我的好友"只需 `WHERE uid = ?`，写入多一次（同事务内，无成本）。

`C:\ProgramData\MySQL\MySQL Server 8.0\Data\spring_cloud\sys_user.ibd`

### 6.2 Redis

| key | 类型 | TTL | 状态 | 说明 |
|---|---|---|---|---|
| `auth:fail:{account}` | STRING 整数 | 15 分钟 | ✅ **在用** | 登录失败计数（防撞库） |
| `auth:sess:{sid}` | HASH：`uid/deviceType/ip/ua/loginAt/lastSeen` | 7 天 | ⏸ 停用 | 精简版后代码不再写入；历史遗留会自然过期 |
| `auth:user:{uid}:ver` | STRING 整数 | 无 | ⏸ 停用 | 精简版后代码不再读写；恢复"即时踢人"时需要它 |

> 停用的两个 key 对应的能力与恢复步骤见 5.3；Redis 里已有的旧 key 不影响运行，可以手动清掉：
> `redis-cli --scan --pattern "auth:sess:*" | xargs redis-cli del`（或忽略，等 TTL 过期）。

> 尚未实现：`auth:user:{uid}:sessions`（设备名册）、`auth:rt:{sid}`（refreshToken）、`auth:revoked:{sid}`（临时黑名单）。

### 8.2 Dubbo（避免与服务名冲突，必须这么配）

```yaml
# 提供方
dubbo:
  application:
    name: user
    register-mode: interface      # 只做接口级注册
# 消费方（auth / ws-gateway）
dubbo:
  application:
    service-discovery:
      migration: FORCE_INTERFACE
```

spring:

## 14. IM 消息链路（已实现）

### 14.1 一次发送的完整时序

```
A 客户端           ws-gateway               im                    RabbitMQ           B 客户端
   │                   │                    │                       │                  │
   │ ①MSG 帧           │                    │                       │                  │
   ├──────────────────▶│                    │                       │                  │
   │                   │ ②取连接身份 userId │                       │                  │
   │                   │   丢业务线程池      │                       │                  │
   │                   │ ③Dubbo send        │                       │                  │
   │                   ├───────────────────▶│                       │                  │
   │                   │                    │ ④幂等 → seq → 事务     │                  │
   │                   │                    │   写 3 条 SQL          │                  │
   │                   │                    │ ⑤提交后发事件          │                  │
   │                   │                    ├──────────────────────▶│                  │
   │ ⑥ACK(cid,seq)     │                    │                       │ ⑦广播给各实例     │
   │◀──────────────────┤◀───────────────────┤                       ├─────────────────▶│
   │                   │                    │                       │                  │
   │                   │◀───────────────────────────────────────────┤ ⑧推给本机连接     │
   │                   ├──────────────────────────────────────────────────────────────▶│
```

### 14.2 ACK 与推送是两条独立的线

| | ACK | 消息推送 |
|---|---|---|
| 触发 | `imClient.send()` 返回后 | MQ 事件被消费后 |
| 目标 | **发送方**（手里有 `ctx`，直写） | **接收方**（不知道连在哪 → 必须广播） |
| 是否依赖对方在线 | 否 | 是（不在线就命中 0 条连接） |
| 失败影响 | 不影响消息存在 | 不影响发送方成功 |

**结论：ACK 只代表"服务端已持久化"，不代表"对方已收到"。**

### 14.3 各环节代码位置

| 环节 | 文件 |
|---|---|
| 收帧 / 身份 / ACK | `ws-gateway/.../handler/BusinessHandler.java` |
| 握手验签 / 写 userId | `ws-gateway/.../handler/AuthHandshakeHandler.java` |
| Dubbo 客户端 | `ws-gateway/.../support/ImClient.java` |
| 落库业务 | `im/.../service/MessageService.java` |
| seq 生成 | `im/.../service/SeqGenerator.java` |
| 事件发布 | `im/.../mq/MessageEventPublisher.java` |
| MQ 消费推送 | `ws-gateway/.../mq/MessagePushListener.java` |
| 连接表 / 推送 | `ws-gateway/.../session/ChannelManager.java` |

### 14.4 失败矩阵

| 失败点 | 发送方看到 | 接收方看到 | 消息是否丢失 |
|---|---|---|---|
| 校验不通过 | 无 ACK（帧被丢弃） | 无 | 未产生 |
| im 抛异常 / 超时 | ACK `seq=0` → "发送失败" | 无 | 未产生 |
| MQ 发送失败 | ACK 正常 | 收不到实时推送（可拉取） | 不丢 |
| MQ 卡住 | ACK 延迟（publish 同步） | 延迟收到 | 不丢 |
| 接收方离线 | ACK 正常 | 无 | 不丢（在库里） |

## 15. WebSocket 接入层（ws-gateway）

### 15.1 职责边界

| 负责 | 不负责 |
|---|---|
| 连接管理、握手验签、协议升级 | 落库、生成 seq |
| 帧编解码、心跳、空闲踢人 | 业务规则（谁能发给谁） |
| 把帧转成 Dubbo 调用 | 知道用户在哪台实例（靠 MQ 广播规避） |
| 消费 MQ 并写回连接 | 消息存储与查询 |

### 15.2 Pipeline（顺序不可调）

```
HttpServerCodec → HttpObjectAggregator → AuthHandshakeHandler
   → WebSocketServerProtocolHandler → IdleStateHandler
   → BusinessHandler → ConnectionHandler
```

关键点：

- `HttpObjectAggregator` 必须在验签之前（否则拿不到完整请求）
- `AuthHandshakeHandler` 必须在升级之前（否则无法回 401）
- `WebSocketServerProtocolHandler` 需 `checkStartsWith(true)`，否则 `/ws?token=xxx` 匹配不上
- `ConnectionHandler` 靠 `HandshakeComplete` 事件登记 connId

### 15.3 帧协议（最小版）

| type | 方向 | 字段 |
|---|---|---|
| `MSG` | 双向 | 上行：`cid` `to` `content`；下行：`from` `seq` `content` |
| `ACK` | 下行 | `cid` `seq`（`seq=0` 表示失败，可带 `code` `reason`） |
| ~~`RECALL`~~ | — | **已移除**（撤回功能下线） |
| `NOTIFY` | 下行 | `event` `from` `content`（好友申请/同意） |
| `PING` / `PONG` | 双向 | 无 |

铁律：`from` / `seq` 只能服务端生成；`cid` 只能客户端生成。

### 15.4 线程模型

```
EventLoop（默认 CPU×2）
  ├─ 解码、校验、心跳（轻量）
  └─ MSG → bizExecutor（8 线程，有界队列 5000，CallerRunsPolicy）
                └─ Dubbo 阻塞调用 → 回调 writeAndFlush
```

- **EventLoop 里绝不做阻塞调用**，否则拖死该线程上的所有连接
- 业务池用有界队列 + `CallerRunsPolicy`：满了由 IO 线程自己跑，形成背压，避免 OOM

### 15.5 心跳与断连

| 项 | 值 |
|---|---|
| 客户端心跳 | 30 秒一次 `PING` |
| 服务端空闲检测 | `IdleStateHandler(0,0,60)` → 触发后 `close` |
| 关闭码约定 | 4001 被踢（不重连）、4002 token 过期（刷新后重连）、4003 服务重启 |

### 15.6 多实例与 MQ 广播

- 每个 `ws-gateway` 实例声明**匿名、独占、自动删除**的队列，绑定同一个 `im.events` 交换机
- 共用队列会变成竞争消费（只有一台收到），**必须每实例一个**
- 消费端按 `toUid` 查本机连接表，命中就写帧，未命中直接丢弃

### 15.7 尚未实现

| 项 | 状态 |
|---|---|

| ~~单端登录踢人（4001）~~ | ✅ 已实现（MQ 广播 kick，见第 19 章） |
| ~~断线重连按 `lastSeq` 补拉~~ | ✅ 已实现（`afterSeq`，见第 18 章） |

### 15.8 限流：令牌桶 + 队列水位

**进线程池之前过两道闸，都不切断连接。**

| 闸 | 参数 | 作用 | 拒绝码 |
|---|---|---|---|
| 令牌桶（每连接） | 速率 **10 条/秒**，桶 **20** | 防"一个人刷" | `429 发送太快` |
| 队列水位 | 队列深度 **> 4000** | 防"大家同时刷" | `503 服务繁忙` |

**令牌桶为什么不用固定窗口**：窗口边界可双倍爆发；令牌桶按时间连续补充，没有毛刺。

**为什么桶要留 20 的容量**：人类会"复制粘贴连发几句"，固定间隔会把它们摊开；桶容量就是给突发留的余量。

**拒绝方式**：

```java
sendFrame(ctx, Frame.nack(in.getCid(), 429, "发送太快，请稍后再试"));
```

| 要点 | 说明 |
|---|---|
| 不断连接 | 用户只是发猛了，不是攻击 |
| **每条都回 ACK** | 不回的话客户端的消息会永远停在"发送中" |
| 日志每秒限一条 | 被刷时保护日志，而不是限制帧（帧很小，约 70 字节） |

**状态放在 handler 成员变量**：每个连接一个 handler 实例，且只在该连接的 EventLoop 线程访问，**不需要加锁**。

**为什么用队列深度当压力信号**：它天然等于"im 处理不过来"，比 CPU、RT 更直接。

## 16. IM 数据模型与 seq

### 16.1 两张表

| 表 | 一行代表 | 索引要点 |
|---|---|---|
| `im_message` | 一条消息 | `uk_conv_seq(conversation_id,seq)` 保序、`uk_client(from_uid,client_msg_id)` 幂等 |
| `im_conversation_member` | 某人在某会话的视图 | `uk_conv_uid` 一人一会话一行、`idx_uid_time(uid,last_msg_at)` 会话列表 |

单聊一个会话 2 行（双方各一行），群聊 N 行。

### 16.2 发一条消息写三条记录（同一事务）

```sql
INSERT im_message (...);
INSERT im_conversation_member (...) ON DUPLICATE KEY UPDATE last_seq=VALUES(last_seq),
    last_read_seq=VALUES(last_read_seq), ...;   -- 发送方：自己发的算已读
INSERT im_conversation_member (...) ON DUPLICATE KEY UPDATE last_seq=VALUES(last_seq), ...;
                                                -- 接收方：只推 last_seq，未读 +1
```

### 16.3 seq 生成

```java
if (!exists(key)) {                       // Redis 被清空/重启
    max = SELECT MAX(seq) FROM im_message WHERE conversation_id=?;
    SETNX key max;                        // 从库里恢复，避免从 1 重来撞唯一键
}
seq = INCR im:seq:{conversationId};       // 原子，并发不撞号
```

要点：seq 是**会话内**连续编号，`id` 是全局自增；事务回滚时 seq 不回退（会有空洞，可接受）。

### 16.4 未读 = 减法（已下线，保留为设计记录）

```sql
last_seq - last_read_seq AS unread
```

不存 `unread_count`，避免"多发/漏加"导致的永久错位。

## 18. 读路径：历史 / 会话列表 / 未读 / 已读

### 18.1 三个接口

| 接口 | 用途 | 关键参数 |
|---|---|---|
| `GET /api/im/messages` | 拉消息（翻历史或补缺口） | `conv` + `beforeSeq` 或 `afterSeq` + `limit` |
| `GET /api/im/conversations` | 会话列表 + 未读 | `limit` |
| ~~`POST /api/im/read`~~ | ~~上报已读位置~~（功能已下线） | — |

三个接口都从 `X-User-Id` 取身份（网关注入），并校验会话归属。

### 18.2 一个接口两种语义

| 参数 | 方向 | SQL | 用途 |
|---|---|---|---|
| `beforeSeq`（默认 0 = 最新） | 往前翻 | `seq < ? ORDER BY seq DESC LIMIT ?` | 打开会话 / 上滑加载 |
| `afterSeq` | 往后补 | `seq > ? ORDER BY seq ASC LIMIT ?` | 断线重连补缺口 |

**都返回升序**：前端拿到就能直接渲染，不用自己反转。

**`hasMore` 的算法**：多取一条（`limit + 1`），多出来了说明还有，然后截掉。

### 18.3 前端分页与合并

| 策略 | 值 | 原因 |
|---|---|---|
| 首次加载 | 30 条 | 首屏够看，请求小 |
| 每次上滑/点击 | 20 条 | 增量友好 |
| 内存上限 | 300 条 | 防止 DOM 无限增长 |
| 去重 | 按 `seq` | 历史 / 实时 / 翻页三者可能重叠 |
| 加载更多后 | `scrollTop += 高度差` | 保证视口不跳 |

**顺序很重要**：先 `loadHistory()` 再 `connect()`，否则实时消息会被历史覆盖。

### 18.4 未读与已读

**未读不存字段**，永远是减法：

```sql
unread = last_seq - last_read_seq
```

**已读上报只增不减**：

```sql
UPDATE im_conversation_member
SET last_read_seq = GREATEST(last_read_seq, ?)
WHERE conversation_id = ? AND uid = ?
```

**前端三个上报时机**：打开会话、正在看的会话收到新消息、重连补齐之后。**同一个 seq 只上报一次**（本地记 `readSent`）。

### 18.5 越权保护

```java
if (!ConversationId.contains(conversationId, uid)) {
    throw new BizException(403, "无权查看该会话");
}
```

`ConversationId.contains("s_1_2", 3)` → false。**所有涉及会话的接口都必须过这一关**，否则改个 `conv` 参数就能读别人的聊天记录。

### 18.6 索引是否用上

| 查询 | 命中索引 |
|---|---|
| `WHERE conversation_id = ? AND seq < ?` | `uk_conv_seq(conversation_id, seq)` range |
| `WHERE conversation_id = ? AND seq > ?` | 同上 |
| `WHERE uid = ? ORDER BY last_msg_at DESC` | `idx_uid_time(uid, last_msg_at DESC)` |

**会话列表不回消息表**——所有展示字段（预览、时间、seq）都在 `im_conversation_member` 里，一张表就够。

## 19. 单端登录与在线表

### 19.1 要解决什么

```
同一个人在手机和电脑上同时登录
   ↓ 消息推两份？未读算谁的？被盗用怎么发现？
   ↓
单端：一个账号同时只允许一条连接，新登录踢掉旧的
```

### 19.2 三段式机制

```
① 新连接握手成功
     → 写入在线表 ws:online:{uid}
     → 广播 KickEvent{uid, excludeConnId=自己, newConnTime}

② 所有实例（含本机）消费该事件
     → 各自查本机连接表
     → 踢掉"该用户 + 不是 excludeConnId + 比 newConnTime 更早"的连接

③ 踢的方式
     → 标记 CLOSE_REASON = KICKED
     → 发 CloseWebSocketFrame(4001) → addListener(CLOSE)
     → 客户端收到 4001 → 不重连
```

**为什么必须广播而不是本机踢**：多实例时旧连接可能在**另一台机器**上，本机表里根本没有。

**为什么必须带 4001**：直接 `close()` 客户端只看到 1006（异常），会当成网络问题自动重连，随后又把新连接踢掉，形成互踢循环。

### 19.3 Redis 在线表

```
key   : ws:online:{uid}          HASH
field : connId
value : 实例地址 127.0.0.1:8089
TTL   : 120 秒
```

| 动作 | 时机 | 命令 |
|---|---|---|
| 登记 | 握手成功 | `HSET` + `EXPIRE` |
| **续期** | **收到客户端 PING（25 秒一次）** | `EXPIRE` |
| 移除 | `channelInactive` | `HDEL connId`（**不是 DEL key**） |

**三条铁律**：
1. 用 HASH 不用 String —— 一个用户可能多条连接，String 会互相覆盖
2. 删除只 `HDEL` 单个 field —— `DEL` 会误删同账号其它连接
3. 必须续期 —— 否则 120 秒后活着的连接被误判离线

### 19.4 竞态与边界

| 边界 | 处理 |
|---|---|
| 遍历时集合被修改（踢人 → 注销 → 删元素） | 先复制成 `List` 再遍历 |
| 踢到自己 | 先踢后登记 + `excludeConnId` 双重防护 |
| **事件乱序**（1 秒内重连两次） | 只踢比 `newConnTime` 更早的连接，旧事件自动失效 |
| 踢一条已半死的连接 | `isActive()` 判断，不活跃就直接 `close()` 触发清理 |
| 旧连接正在处理消息 | 落库成功但 ACK 写不进去（`isActive=false`）→ 用户重连后能从历史里看到 |
| 两台设备同时握手 | 都带着"自己是最新"的时间戳，可能都存活（**已知局限**） |

### 19.5 关闭码约定

| 码 | 含义 | 客户端行为 |
|---|---|---|
| 1006 | 异常断开（没有 Close 帧） | 自动重连 |
| 1009 | 单帧超 4KB | 不重连，提示"消息过大" |
| **4001** | **同账号在别处登录** | **不重连**，提示"已在其他设备登录" |
| 4002 | token 过期（未实现） | 不重连，提示重新登录 |
| 4003 | 服务重启（未实现） | 退避重连 |

### 19.6 还没做

| 缺口 | 说明 |
|---|---|
| 频率限制 | 单端只解决"几条连接"，没解决"发多快" |
| 在线状态接口 | `OnlineRegistry.list()` 已就绪，尚未暴露 HTTP |
| 设备维度单端 | 需要 token 里带 `dev`，才能做"同类型互踢、不同类型共存" |
| 强制下线 | 需要 `sid/ver`，属于 P3 |

## 20. 注册与账号安全

### 20.1 注册流程

```
POST /api/auth/register {account, password, nickname}
   ↓ auth：格式校验 → BCrypt 哈希（明文不落库、不落日志）
   ↓ Dubbo → user.create(CreateUserCmd)
   ↓ INSERT sys_user（唯一索引兜底，撞了返回 409）
   ↓ Dubbo → im.ensureFriend(userId, adminUid)   ← 失败只记日志
   ↓ 签发 token（注册即登录）
   ↓ 返回 {userId, nickname, accessToken, expiresIn}
```

**三个要点**：

| 点 | 说明 |
|---|---|
| **唯一性靠数据库** | 不做"先查后插"（并发下两个请求都会通过），直接插入并捕获 `DuplicateKeyException` |
| **密码只存在一次** | `encode` 后明文即弃；`CreateUserCmd` 传的是哈希，user 服务不接触明文 |
| **注册不能让社交失败拖垮** | 自动加管理员失败只 warn，下次登录前端还能兜底 |

### 20.2 校验规则

| 字段 | 规则 | 理由 |
|---|---|---|
| `account` | 4~20 位 `[a-z0-9_]`，**统一转小写** | 避免 `Admin`/`admin` 变成两个账号 |
| `password` | 8~20 位，必须含字母+数字 | 纯数字或纯字母太弱 |
| `nickname` | 1~16 字，允许重复 | 重名是正常社交现象 |

### 20.3 账号枚举防护

```
账号不存在 / 密码错误  →  返回同一句"账号或密码错误"
```

**否则攻击者可以先批量探测"哪些账号存在"，再做定向撞库。**

### 20.4 尚未做

| 项 | 影响 |
|---|---|
| 注册 IP 限流 | 可被脚本批量注册 |
| 手机/邮箱 + 验证码 | 无通道，暂不做 |
| refreshToken | 30 分钟后需重新登录 |

## 21. 好友体系

### 21.1 规则

```
① 注册成功 → 自动与管理员(uid=1)成为好友
② 想和谁聊天 → 必须先有好友关系
③ 非好友发消息 → 服务端拒绝（不是前端藏输入框）
```

**第 ③ 条必须在后端做**：前端隐藏 UI 挡不住任何人用脚本直连 WS。

### 21.2 加好友流程

```
A：GET /api/user/search?keyword=xiaohong     ← 只支持完整账号，精确匹配
   POST /api/im/friends/requests {toUid, message}
      ↓ 校验：不能加自己、不能已是好友、消息 ≤100 字
      ↓ INSERT ... ON DUPLICATE KEY UPDATE（重复申请覆盖，不新增）

B：GET /api/im/friends/requests               ← 拉待处理（前端 20 秒轮询）
   POST /api/im/friends/requests/{id}/accept
      ↓ 事务：UPDATE status=1 + 建双向好友
```

### 21.3 搜索为什么只做精确账号

| 方案 | 结果 | 问题 |
|---|---|---|
| 前缀/模糊 | 输入 `xiao` 列出 4 人 | 慢（`%x%` 全表扫）、能被用来批量抓用户 |
| **精确账号** | 0 或 1 条 | 记不住账号就找不到人（后续可加昵称结果列表） |

### 21.4 非好友发消息的拦截点

```
WS 帧 MSG → BusinessHandler → Dubbo → im.MessageService.send()
                                          ↓
                                   FriendService.isFriend(from, to)
                                          ↓ 否
                                   BizException(403, "请先添加好友再聊天")
                                          ↓
                    ws-gateway 捕获 → ACK {seq:0, code:403, reason:"..."}
```

**为什么放在 im**：好友关系在 im 的库里，ws-gateway 只做转发，不该懂业务规则。

**代价**：每条消息多一次 `uk_uid_friend` 查询（主键级，0.1ms）。

### 21.5 数据一致性

| 场景 | 处理 |
|---|---|
| 同意申请时崩溃 | 事务包裹"标记 + 建关系"，不会出现"同意了却没成好友" |
| 重复同意 | SQL 带 `status = 0`，第二次影响 0 行 → 抛"该申请已处理" |
| 越权同意别人的申请 | SQL 带 `to_uid = ?`，改 id 也处理不了别人的 |
| 并发重复申请 | 唯一键 + `ON DUPLICATE KEY UPDATE`，只留一条记录 |

### 21.6 尚未做

| 项 | 说明 |
|---|---|
| ~~实时推送申请~~ | ✅ 已实现：MQ `ws.notify` → `NOTIFY` 帧（见第 22 章） |
| 删好友 / 备注名 | `im_friend.status`、`remark` 字段已留 |
| 黑名单 | 需要独立表或 `status=2` |

## 22. 前端交互与体验细节

### 22.1 消息渲染规则

| 规则 | 做法 | 为什么 |
|---|---|---|
| **时间分隔** | 第一条 / 跨天 / 间隔 >5 分钟才插一行 | 每条都显示时间会淹没内容 |
| **系统消息** | `from=0` → 居中灰胶囊，不显示 seq | 它不是"谁说的"，而是"系统通知" |
| **去重** | 实时与历史按 `seq` 去重 | 历史与推送可能重叠 |
| **内存上限** | 最多 300 条，超出丢弃最老的 | 防 DOM 无限增长 |

### 22.2 滚动策略（不抢用户的滚动条）

```js
if (force || atBottom()) scrollToBottom()
else unreadNew++          // 右下角浮出「↓ N 条新消息」
```

| 场景 | 行为 |
|---|---|
| 自己发消息 / 系统消息 | `force=true`，一定滚到底 |
| 对方发消息，且在底部 | 自动滚到底 |
| 对方发消息，但你在翻历史 | **不动**，显示"N 条新消息"按钮 |

**判断"是否贴底"要在插入消息之前**（否则刚插入的内容会让判断失真）。

### 22.3 消息状态机

```
sending ──ACK seq>0──▶ sent
   │
   └──ACK seq=0──▶ failed ──点击气泡──▶ sending（用同一个 cid 重发）
```

**重发为什么安全**：服务端 `uk_client(from_uid, client_msg_id)` 唯一 →
即使上次其实成功只是 ACK 丢了，重发也只返回原来的 seq，不会产生两条。

### 22.4 连接状态与用户出口

| 状态 | 界面表现 | 出口 |
|---|---|---|
| `connecting` / `closed` | 消息区顶部黄条"正在尝试重连…" | 自动重连（1s/2s/4s/8s/10s 退避） |
| `kicked`（4001） | "已在其他设备登录" | **不重连** + 「重新登录」按钮 |
| `too-big`（1009） | "消息过大，已被断开" | 提示刷新页面 |
| `token-expired`（4002） | "登录已过期" | 「重新登录」按钮 |

**原则**：服务端主动断开时，必须给用户一个明确的下一步，不能只在角落变个颜色。

### 22.5 会话列表

| 行为 | 说明 |
|---|---|
| 置顶 | 收到消息时把该会话 `splice + unshift` 到首位 |
| 未读 | `last_seq - last_read_seq`，打开会话即上报已读并清零 |
| 预览 | 发送/接收时同步更新最后一条内容 |

### 22.6 好友通知

```
收到 NOTIFY(friend_request) → 顶部蓝条"XX 请求添加你为好友" + 申请红点
收到 NOTIFY(friend_accepted) → 刷新好友列表 + 蓝条
```

蓝条 5 秒自动消失；连接建立/重连时再拉一次列表作为兜底（防通知丢失）。

## 23. 撤回 / 在线状态 / 桌面通知

### 23.1 消息撤回

#### 规则

```
只能撤自己发的 → 只能撤 2 分钟内的 → 不能重复撤
```

#### 为什么是"软删"而不是 `DELETE`

```
seq 必须连续：
  删掉 seq=26 这行 → last_seq=30，但中间缺 26
  → 客户端 afterSeq 补缺口时永远等不到 26
  → 未读数 last_seq - last_read_seq 也会错
所以：行保留，content 置空，recalled = 1
```

#### 链路

```
客户端 RECALL{cid, to, seq}
   ↓ ws-gateway：限流 → 线程池 → Dubbo
   ↓ im.recall(uid, toUid, seq)
        ① 算会话 s_min_max
        ② 查消息：不存在 404 / 不是本人 403 / 已撤回 400 / 超 2 分钟 400
        ③ UPDATE ... SET recalled=1, content='' WHERE ... AND from_uid=?
        ④ 会话预览改成「[消息已撤回]」（只改 last_seq 命中那行）
        ⑤ MQ ws.notify → event=message_recalled（content 放 seq）
   ↓ ACK{cid, seq} 回给撤回者；失败回 nack(code, reason)
   ↓ 对方收到 NOTIFY → 本地那条置为「对方撤回了一条消息」
```

#### 四个设计点

| 点 | 说明 |
|---|---|
| 权限校验写在 SQL 里 | `AND from_uid = ?` —— 从数据库层面杜绝"撤别人的消息"，不靠应用层判断 |
| 不回消息内容 | 通知里只带 seq，撤回的东西不该再传一遍 |
| 通知丢了也不影响 | 历史接口返回 `recalled`，重新打开会话照样正确 |
| 和发消息共用限流/线程池 | 撤回同样是 Dubbo 阻塞调用，不能在 EventLoop 里 |

### 23.2 在线状态

```
数据源：ws-gateway 写的 ws:online:{uid}（HASH + TTL 120s）
读的人：im（只读不写）
刷新：前端 60 秒拉一次好友列表
```

**为什么 im 只读**：在线状态的真相在接入层（连接在哪、活着没有）。如果业务层再存一份，两边不一致时必须判断"信谁"，这是自找麻烦。

**为什么不用心跳实时推在线状态**：好友上下线非常频繁，推一次要广播给所有好友，代价远大于"60 秒拉一次"。

**Redis 不可用时一律返回离线**——宁可显示灰点，也不要显示一个假的在线。

### 23.3 桌面通知与标题未读

| 项 | 做法 | 原因 |
|---|---|---|
| 标题 | `document.title = "(3) IM"` | 切到别的标签页也能看到未读 |
| 桌面通知 | 仅 `document.hidden` 时弹 | 正在看就没必要打扰 |
| 权限 | 登录后请求一次，拒绝后不再问 | 反复弹权限框很烦 |
| 触发条件 | 消息**不属于当前打开的会话** | 当前会话已经算已读 |

**通知只是"提醒"**：点不点、弹不弹，都不影响数据正确性（未读落库、历史可拉）。

### 23.4 尚未做

| 项 | 说明 |
|---|---|
| 通知点击跳转会话 | 需要 `Notification.onclick` + 窗口聚焦 |
| 多端通知合并 | 同账号多端时会各弹一次（单端登录后基本不存在） |

## 24. 后台管理与凭证作废

### 24.1 权限模型

```
sys_user.role: user | admin
   ↓
网关：只验签，注入可信 X-User-Id（不改 JWT 加 role）
   ↓
各服务：拿到 uid 后自己查 role，非 admin 抛 403
```

**为什么不把 role 写进 JWT**：

| 方案 | 问题 |
|---|---|
| 写进 JWT | 改角色要等 token 过期才生效；JWT 结构也要改 |
| **服务内查库 / Dubbo** | 改角色立即生效；JWT 不动 |

**前端隐藏按钮只是体验，接口必须自己校验**——直接 curl 也能测出来。

### 24.2 五个后台接口

| 接口 | 归属服务 | 关键点 |
|---|---|---|
| `GET /api/admin/users` | user | 支持账号/昵称模糊搜索（后台才允许模糊） |
| `POST /api/admin/users/{id}/status` | user | **"删除"= 禁用**（status=0），不能禁自己 |
| `POST /api/auth/admin/users/{id}/password` | auth | 密码策略与 BCrypt 只存在于 auth |
| `GET /api/im/online?uids=` | im | 读 `ws:online:{uid}` |
| `POST /api/im/admin/kick/{uid}` | im | 断连接 + 作废 token，不能踢自己 |

网关新增一条路由：

```yaml
- id: admin
  uri: lb://user
  predicates: [Path=/api/admin/**]
  filters: [StripPrefix=1]     # /api/admin/users → /admin/users
```

### 24.3 "删除用户"为什么是禁用

```
消息表里存着 from_uid
   ↓ 物理删除用户
   ↓ 历史消息变成"孤儿作者"（查不到昵称、点头像 404）
   ↓ 好友关系、会话卡片也跟着悬空
所以：status=0（禁用）—— 登录被拒，数据仍完整可追溯
```

### 24.4 凭证作废（解决"踢完刷新又上线"）

**问题**：踢人只关闭连接，token 还在客户端手里，F5 一下就回来了。

**解法**：踢人时记一条"时间线"，之后所有"签发时间早于它"的 token 一律拒绝。

```
踢人 → SET auth:kicked:{uid} = now  (TTL 30 分钟)
     → MQ ws.kick 断开当前连接

网关每次请求：iat < 作废线 → 401
WS 握手：同样判断 → 401（刷新直连 8089，不走网关，必须单独校验）
前端：收到 401 → 清 token → 回登录页（已有逻辑）
```

**四个设计点**：

| 点 | 说明 |
|---|---|
| 不记具体 token | 没有 `jti` 定位不了单条，按 `iat` 批量作废效果等价 |
| TTL = token 有效期 | 30 分钟后旧 token 本就过期，记录可自动消失，不用维护 |
| Redis 故障放行 | 可用性优先，宁可短暂放过旧 token，也不要全员掉线 |
| **单端登录不写作废线** | 否则换个浏览器登录，旧的连刷新都进不来 |

### 24.5 踢下线 vs 封禁

| | 踢下线 | 封禁（禁用） |
|---|---|---|
| 动作 | 断连接 + 作废当前 token | `status = 0` |
| 用户能否再登录 | **能**（重新登录拿到新 token） | **不能** |
| 场景 | 强制重新认证、异常设备 | 违规处理 |

**两个按钮，两种语义，不要混用。**

### 24.6 尚未做

| 项 | 说明 |
|---|---|
| 操作审计表 | 现在只打日志，没有 admin 操作记录表 |
| 角色管理界面 | 只有 user/admin 两档，改角色需直接改库 |
| 批量操作 | 只能一个一个点 |
| 踢人原因/通知 | 4001 文案固定，无法告诉用户"为什么被踢" |

## 25. Outbox：让"要发 MQ"也变成"写数据库"

### 25.1 之前的问题

```java
@Transactional
public SendResult send(...) {
    insert(message);           // ① 落库
    upsertMembers(...);
    afterCommit(() -> publish(event));   // ② 提交后发 MQ ← 失败只打日志
}
```

**这是"双写"**：数据库和 MQ 是两个系统，无法原子。

| 故障点 | 后果 |
|---|---|
| MQ 挂了 / 网络抖动 | 消息在库里，但**推送永久丢失**，且没人知道 |
| 发完 MQ 进程崩溃（在标记之前） | 取决于崩溃点，可能丢可能重 |
| 消费端问题 | 同上 |

**关键矛盾**：`afterCommit` 只保证"提交后才发"，不保证"一定发出去"。

### 25.2 改法：把"发 MQ"写进同一个事务

```
事务内：写 im_message + im_message_member + **im_outbox（一条待办）**
   ↓ 提交
定时任务（每秒）：扫 outbox 待发 → 真的发 MQ → 成功才划掉
```

**语义变化**：

```
改前：落库成功 + 推送尽力而为（至少 0 次，可能丢）
改后：落库和待办同生共死 + 后台无限重试（至少 1 次，不丢）
```

### 25.3 表结构与状态机

```sql
CREATE TABLE im_outbox (
  id, event_type, payload,     -- 事件类型 + JSON
  status,                      -- 0待发 1发送中 2已发 3死信
  retry, next_retry_at,        -- 重试次数 + 退避后的下次时间
  created_at, sent_at
);
KEY idx_pending (status, next_retry_at, id)
```

```
0 待发 ──抢占──> 1 发送中 ──成功──> 2 已发（72 小时后清理）
                      └──失败──> 0（退避重试）──5 次后──> 3 死信
                      └──卡住 60 秒──> 0（回收重发）
```

### 25.4 四个实现要点

| 点 | 做法 | 为什么 |
|---|---|---|
| **抢占要原子** | `SELECT ... FOR UPDATE SKIP LOCKED` + 立即置 1 | 多实例同时扫不会重复处理，也不会互相阻塞 |
| **发 MQ 在事务外** | 先在事务 A 里抢占用，提交后再发 | 避免长事务把行锁一直握着 |
| **失败指数退避** | 1s / 2s / 4s / 8s / 16s，5 次后死信 | 防止 MQ 长时间故障时把表刷爆 |
| **卡死回收** | `status=1` 且超过 60 秒 → 重置为 0 | 进程崩溃时的残留必须能自愈 |

**清理策略**：`status=2` 的记录保留 72 小时后删除（便于排查），死信保留人工处理。

### 25.5 诚实地说：这是"至少一次"

```
发 MQ 成功 → 还没标记已发时进程崩溃
   ↓ 重启后重新发送
   ↓ 消费端收到两次
```

**所以必须幂等**：我们的消息事件带 `seq`，ws-gateway 推送前按"已推 seq"比对，
重复的直接丢弃。

#### 消费端幂等怎么做的

```java
// 每条连接挂一份 Map<fromUid, 最近 N 个 seq 的窗口>（LRU 上限 500 个会话）
Deque<Long> window = recentSeq.computeIfAbsent(fromUid, k -> new ArrayDeque<>(32));
if (window.contains(seq)) {
    continue;                    // 只挡"完全相同"的重复
}
channel.writeAndFlush(frame);
window.addLast(seq);
if (window.size() > 32) window.removeFirst();
```

| 设计点 | 原因 |
|---|---|
| **只判"相等"，不判大小** | 见下方踩坑记录：Outbox 不保序，用 `seq <= last` 会误杀乱序消息 |
| 窗口只留 32 条 | MQ 重投窗口是秒级，同会话几秒内不会有 32 条重复；窗口外漏网由前端 `seq ===` 兜住 |
| 按 `fromUid` 而不是会话 ID | 单聊里 `fromUid` 唯一确定会话，省一次字符串拼接 |
| **写成功才入窗口** | 连接不可写（出站积压）时算"没推过"，下次补推不会被自己挡住 |
| LRU 上限 500 个会话 | 防止长连接 + 大量会话导致 Map 无界 |
| 放在 ws-gateway 而不是前端 | 前端也要去重，但**未读数**在前端加 1，服务端挡掉才是最干净的 |

#### 踩坑记录：用"最大 seq"判重会丢消息

第一版实现是水位线语义：

```java
Long last = pushedSeq.get(fromUid);
if (last != null && seq <= last) continue;   // ❌ 隐含"必然有序"
pushedSeq.put(fromUid, seq);
```

**错在哪**：`seq` 由 Redis INCR 连续分配，但"发送"这一步有三条乱序来源：

| 乱序来源 | 机制 |
|---|---|
| 并发抢占 | `wakeUp` 线程与 5 秒扫表线程各抢一批，谁先发完谁先到 MQ |
| **失败重试** | seq=25 发送失败退避 1 秒，26/27 已到 → 25 补发时 `25 <= 27` 被丢弃 |
| 多实例 | im 扩容后 25 从实例 1 发、26 从实例 2 发，网络路径不同 |

**最讽刺的是第二条**：Outbox 存在的意义就是"失败能补发"，结果补发上来的消息被自己的去重逻辑吃掉。
一次 MQ 抖动就能让重发的几条全部消失，而且**用户不刷新就永远看不到**。

**结论**：用 `max(seq)` 当水位线，前提是"消息严格有序到达"。至少一次 + 并发/重试的系统里没有这个前提，
只能用"最近 N 个 seq 的集合"做精确判重——**幂等是集合语义，不是大小语义**。

**端到端验证**（真实 WS 连接 + 向 MQ 灌乱序事件）：

```
1) 发 seq=101  → 客户端收到 101
2) 发 seq=100  → 客户端收到 100     ← 乱序的小 seq 不会被误杀
3) 再发 seq=101 → 客户端无任何收到   ← 完全重复被挡住
```

#### 配套：前端按 seq 插入而不是 append

既然承认"到达可能乱序"，展示层也不能盲目追加：

```js
const pos = messages.value.findIndex((m) => typeof m.seq === 'number' && m.seq > frame.seq)
if (pos === -1) pushMessage(incoming)        // 正常追加（顺带处理滚动）
else messages.value.splice(pos, 0, incoming) // 补到中间，不打扰正在翻历史的用户
```

**实测**（向 MQ 灌两条完全相同的事件）：

```
第 1 次 → 推送消息 to=1 from=2 seq=99999 命中连接数=1   ← 正常推送
第 2 次 → 推送消息 to=1 from=2 seq=99999 命中连接数=0   ← 被幂等跳过
```

> 想要"恰好一次"，就得在消费端做去重表或在 DB 里记录消费位点——成本高，聊天场景不值得。
> "至少一次 + 消费端按 seq 幂等"已经等价于业务上的恰好一次。

### 25.6 上线与验证

```bash

# 2. 重启 im（@EnableScheduling 已加）
docker restart im-im
# 3. 发一条消息后查

#    status=2 + sent_at 有值 = 投递成功
```

```

   ↓ 消息正常显示（落库 + ACK 都成功）
   ↓ 对方收不到（MQ 停了）
   ↓ outbox 里 3 条 status=0
docker start campus-rabbitmq     → 1~2 秒后全部 status=2，对方收到
```

### 25.8 延迟优化：提交后立即唤醒

**只靠每秒扫表，推送会慢半拍**：平均 0.5 秒、最长 1 秒，聊天场景能感觉到。

```
事务提交 → 等下一次扫表（0~1000ms）→ 发 MQ → 推给对方
```

**改法**：提交后主动叫醒投递器，定时器退化成兜底。

```java
// MessageService：提交后立即唤醒
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        outboxRelay.wakeUp();
    }
});

// OutboxRelay：合并高频唤醒，同一时刻只排一个任务
public void wakeUp() {
    if (!wokeUp.compareAndSet(false, true)) return;
    taskScheduler.schedule(() -> { wokeUp.set(false); relay(); }, Instant.now());
}
```

**实测对比**（`created_at → sent_at`）：

| 方式 | 投递延迟 |
|---|---|
| 只靠每秒扫表 | 374 ms、714 ms |
| **立即唤醒 + 扫表兜底** | **155 ms** |

**为什么定时扫表不能删**：

| 场景 | 依赖 |
|---|---|
| 正常发消息 | afterCommit 唤醒（≈0） |
| 进程崩溃后的残留 | 扫表（含 60 秒卡死回收） |
| MQ 恢复后的退避重试 | 扫表（看 `next_retry_at`） |
| 唤醒本身失败/丢失 | 扫表 |

**"立即推 + 定期扫"是 Outbox 的标准姿势**：定时器不是主路径，而是安全网。

## 26. 多端登录

### 26.1 从单端到多端

早期是**单端登录**：新连接握手后广播 `ws.kick`，把该账号的旧连接全部踢掉（4001，客户端不重连）。

改成多端只做了一件事：**握手时不再广播 kick**。基础设施本来就是多端结构：

| 组件 | 为什么天然支持多端 |
|---|---|
| `ChannelManager.userChannels` | `Set<Channel>`，一个 uid 可挂多条连接 |
| `ws:online:{uid}` | Redis HASH，field = connId，本来就能存多个 |
| `pushToUser` | 遍历该 uid 的所有连接逐个推 |

管理员强制下线仍走 `AdminKickPublisher`（`ws.kick`），不受影响。

### 26.2 核心问题：自己发的消息，别的端收不到

推送原本只查**接收方**（`toUid`）的连接，所以：

```
手机发"在吗" → 小红的所有端收到 ✅
             → 自己电脑上什么都没有 ❌
```

要改成推两拨人：

```
推送目标 = toUid 的全部连接  ∪  ( fromUid 的全部连接 － fromConnId )
            ↑ 对方多端            ↑ 自己多端，但要减掉"发消息那条"
```

**为什么必须排除 `fromConnId`**：那条连接上的客户端已经本地渲染 + 收到 ACK，再推一次等于自己收自己的消息（浪费一次推送，还多一层去重依赖）。

### 26.3 connId 为什么要一路传到 MQ

`connId` 只存在于 ws-gateway 的 `Channel` 属性里，而推送发生在 MQ 消费线程，两者跨进程：

```
BusinessHandler（读 Channel.CONN_ID）
  → ImClient → SendMessageCmd（Dubbo 契约）
  → ImMessageFacadeImpl → SendRequest
  → MessageService（落库 + 写 Outbox）
  → MessageEvent（JSON 进 im_outbox.payload）
  → MQ → MessagePushListener（终于又拿到 connId）
```

**信息不会自己流动，每过一道边界就要显式搬一次**——这是跨进程通信的成本，不是啰嗦。

### 26.4 推送实现

```java
// MessagePushListener
Frame out = Frame.down(fromUid, seq, content);

// ① 接收方全部连接
int online = channelManager.pushMessageOnce(toUid, fromUid, seq, out);

// ② 发送方其它连接（排除发消息那条）
int echoed = channelManager.pushToUserExcept(fromUid, fromConnId, fromUid, seq, out);
```

两者共用 `writeIfNew`：同一条消息（同 `fromUid` + `seq`）对同一条连接只写一次，吸收 Outbox 的重复投递。

### 26.5 前端：区分"自己发的"

```js
const isSelf = frame.from === profile.value.id

// 渲染成自己的蓝色气泡，而不是对方的灰色
mine: isSelf

// 自己发的同步帧不加未读、不弹桌面通知
if (!isSelf) { ... }
```

去重仍按 `seq` 精确匹配（不区分 mine），否则同一条会被插两次。

### 26.6 踩坑：Jackson 只认 getter

`MessageEvent` 加了 `private String fromConnId` 但**没加 getter** 时：

```
writeValueAsString(event) → JSON 里根本没有这个字段
消费端 node.path("fromConnId") → null
多端同步永远不生效，编译通过、日志正常、不报错
```

**规律：跨进程序列化的 DTO（Dubbo 契约 / MQ 事件 / Outbox payload）加字段，
必须同时确认 ① 字段 ② getter/setter ③ 构造赋值 ④ 消费端读取。少一样就是静默失效。**

### 26.7 当前边界

| 能力 | 状态 |
|---|---|
| 同账号多端在线 | ✅ |
| 自己发的消息同步到其它端 | ✅ |
| 别人发的消息推到所有端 | ✅ |
| 已读跨端同步 | —（已读功能整体下线） |
| 撤回跨端同步 | —（撤回功能整体下线） |
